# 새 GPU 첫 실행 체크리스트

4090 / H100 / 그 다음. **전수 측정을 켜기 전에** 통과해야 하는 게이트다.

이 문서는 절차서이고, 각 게이트의 *이유*는 다른 문서에 있다. 링크를 따라
읽되, **순서를 바꾸지 마라** — 뒤의 게이트는 앞의 게이트가 통과했다는 것을
전제로 판정한다.

---

## 왜 7 시간을 미리 쓰는가

A6000 에서 이 절차 없이 시작했고, 두 번 대가를 치렀다.

| 무엇 | 대가 | 어느 게이트가 막았을 것인가 |
|---|---|---|
| 드리프트를 모르고 전수를 켰다 | **7.5 시간 / 226,145 행 폐기** (전체의 23 %) | G-4 |
| 검증 없이 전수를 켰다 | 3 시간 검증 실행에서 **버그 4 개** | G-7 |

폐기한 쪽이 더 아팠던 이유는 시간이 아니다. **감시하고 있었는데도 못 봤다.**
4096³ 프로브 하나로 지켜보며 "+5.06 % 니까 견딜 만하다" 고 판단했는데,
같은 시각 512³ 측정은 **+1380 % 오염**돼 있었다. 드리프트는 런치당 상수라
긴 커널에서는 안 보인다. 감시 지표를 잘못 골랐다는 사실 자체를 몰랐다.

3 시간 검증에서 나온 버그 4 개는 전부 "돌기는 도는데 틀린" 종류였다.

1. `drift_kernel_id = picked[0]` 이 세그먼트 필터 **이전** 목록을 참조 → KeyError
2. `WARMUP_SECONDS` 를 정의만 하고 쓰지 않음. soak 을 끄면 워밍업이 통째로
   사라지는데 **로그는 "워밍업만 한다" 를 찍었다**
3. `zstd` 가 append-only 파일과 경쟁해 exit 27
4. `MEM_CLOCK_MIN_FRAC` 미구현 (AST 감사로 발견)

전수 33 시간 뒤에 이것들을 발견했다면 33 시간이 날아갔다.

**선행 절차 ~7 시간 vs 캠페인 ~33 시간.** 21 % 를 보험료로 쓴다.

## G-0. 이미지와 환경

컨테이너 이미지는 `docker/Dockerfile.draft` 의 다이제스트를 그대로 쓴다.

```bash
TAG=$(python3 scripts/manifest.py --tag)     # kerneltab:cu124-xxxxxxxx
```

> ⚠️ **CUDA 버전을 올리지 마라.** nvcc 버전은 `env_hash_v2` 의 입력이다
> (`core/env_hash.py`). 올리면 새 `env_hash` 가 되고 기존 표와 절대 시간을
> 비교할 수 없다. Blackwell 처럼 **필요해서** 올리는 것은 새 캠페인이지
> 이전이 아니다.

GPU 는 UUID 로 지정한다. 인덱스는 `CUDA_VISIBLE_DEVICES` 와 컨테이너
`--gpus` 를 거치며 뜻이 바뀐다 (`core/device.py`). UUID 를 못 찾으면
코드가 **실패한다** — 조용히 0 번으로 가지 않는다.

```bash
nvidia-smi --query-gpu=index,uuid,name --format=csv
```

## G-1. 클럭 고정 (호스트에서)

컨테이너 안에서는 불가능하다. `nvidia-smi -lgc/-lmc` 는 `CAP_SYS_ADMIN` +
드라이버 쓰기 접근이 필요하고 컨테이너 툴킷은 주지 않는다.

```bash
sudo nvidia-smi -i <IDX> -pm 1
sudo nvidia-smi -i <IDX> -lgc <MHZ>,<MHZ>
sudo nvidia-smi -i <IDX> -lmc <MEM_MHZ>
python3 scripts/verify_clock_lock.py --minutes 5
```

**`-lgc` 는 SM 클럭만 잠근다.** 메모리 클럭은 따로 잠가야 한다. 잠그지
않으면 roofline 의 분모가 흔들리고 `is_memory_bound` 가 전부 틀린다.

고정이 안 되는 환경이면 그대로 진행해도 된다 — 코드가 graceful 하게
처리한다. 다만 드리프트 점검 주기가 10 분 → 3 분으로 짧아지고 재현성이
나빠진다 (A6000 실측: 미고정 max 8.91 % vs 고정 max 0.35 %).

## G-2. P-state 확인 — 요청값이 그대로 걸리지 않는다

**컴퓨트 워크로드는 P2 로 떨어지고, P2 의 메모리 클럭은 P0 최대치보다 낮다.**
A6000 은 8001 MHz 를 요청했지만 부하 중 실측은 **7601 MHz** 였다.

```bash
nvidia-smi -i <IDX> --query-gpu=pstate,clocks.sm,clocks.mem --format=csv -l 2
```

요청값이 아니라 **실측값**을 조건으로 기록한다.

```bash
python3 scripts/phase0_env.py --device 0 \
    --externally-locked-mhz <실측 SM> --externally-locked-mem-mhz <실측 MEM>
```

실측이 요청의 90 % 미만이면(`MEM_CLOCK_MIN_FRAC`) 워밍업이 게이트를 걸고
넘어가지 않는다.

## G-3. 실효 피크와 ridge point

고정된 클럭에서의 실효 TFLOP/s 와 대역폭을 잰다. **스펙 시트 값을 쓰지
마라.** A6000 스펙은 154.8 TFLOP/s · 768 GB/s 인데 고정 클럭 실측은 그보다
낮고, ridge point 가 여기서 나온다. 틀리면 `is_memory_bound` 가 전부 틀린다.

`phase0_env.py` 가 `peak_tflops_f16_effective` / `bandwidth_gbps_effective`
로 기록한다. 스펙 대비 60~90 % 밖이면 클럭 고정이나 측정 자체를 의심하라.

## G-4. ⛔ 드리프트 3 값 — **건너뛰지 마라**

한 프로세스가 서로 다른 커널을 많이 실행하면 **런치당 상수 오버헤드**가
커진다 (CUDA 12.4 의 LAZY 모듈 로딩, `docs/measurement_drift.md`). 크기도
문턱도 하드웨어에 의존하므로 **GPU 마다 다시 재야 한다.**

얻을 값 세 개:

| 값 | 뜻 | A6000 |
|---|---|---|
| **문턱** | 몇 개까지는 `a` 가 전혀 안 늘어나는가 | ~1,200 모듈 |
| **문턱 위 기울기** | 모듈 1,000 개당 `a` 증가량 | ~75 us |
| **왜곡 배율** | 가장 짧은 커널 대 가장 긴 커널의 드리프트 비 | ~100 배 |

> 전 구간 평균으로 재면 42 us/1,000 이 나온다 (문턱 아래 평탄 구간이
> 섞여서다). 세그먼트 크기를 정하는 데 쓰는 것은 **문턱 위 기울기**다.

방법: 커널을 아주 작은 문제로 하나씩 "터치" 해 모듈을 쌓으면서, 기준 커널
여러 개를 **여러 형상에서** 재고 `t = a + b·work` 를 맞춘다. 드리프트는
`a` 에만 나타나야 한다 (`b` 가 같이 움직이면 다른 원인이다 — 클럭·발열을
의심하라).

> ⚠️ **큰 형상 하나로 재면 안 된다.** 짧은 커널이 반드시 있어야 한다.
> A6000 에서 4096³ 만 보고 +5.06 % 로 판정했는데 512³ 은 +1380 % 였다.

```bash
kerneltab drift --gpu <UUID> --max-touch 3000 --step 100
#   -> results/drift_profile.json  (threshold / us_per_1k / distortion /
#                                   recommended_segment_kernels)
```

`scripts/measure_drift.py` 가 이것을 한다. **A6000/CUDA 12.4 에서 이미
알던 값을 재현하는지로 검증했다:**

| | 임시 스크립트 (원래 조사) | `measure_drift.py` |
|---|---|---|
| 문턱 | ~1,200 모듈 | **1,154** |
| 문턱 위 기울기 | ~75 us/1,000 | **77.4** |
| 권장 세그먼트 | 500 (실제로 쓴 값) | **461** |
| `b` 변화 | ~0 | **-3.42%** |

그리고 **같은 GPU 를 CUDA 13.3 에서 다시 재니 값이 달라졌다** — 이 게이트가
GPU 마다가 아니라 **툴체인마다** 필요하다는 증거다.

| | CUDA 12.4 | CUDA 13.3 |
|---|---:|---:|
| 문턱 | 1,154 | **962** |
| 기울기 | 77.4 us/1,000 | **50.6** |
| 권장 세그먼트 | 461 | **384** |

`b`(계산 속도)가 거의 안 움직이는데 `a`(런치 상수)가 16.7 -> 130.6 us 로
**7.8 배**가 된 것이 판별의 핵심이다. 발열이나 클럭이면 `b` 가 함께 움직인다.

> ⚠️ 왜곡 배율은 정의가 두 가지다. 원래 조사는 **커널 길이의 비**(15us 대
> 22ms = 100배)를 썼고, 이 스크립트는 **상대 드리프트의 비**
> (256³ +1079% 대 4096³ +4.4% = 243배)를 쓴다. 후자가 "짧은 커널이 얼마나
> 더 왜곡되는가" 라는 질문에 직접 답한다. 숫자를 인용할 때 어느 쪽인지
> 밝힐 것.

> 터치 실패율도 함께 본다. A6000 에서 3,000개 중 **371개(12.4%)** 가
> 런치 불가 커널이었다 (`regs * threads > 65,536`, CUTLASS status 7).
> 압력 축이 그만큼 짧아지므로 실패를 세지 않으면 문턱이 틀린다.

## G-5. 세그먼트 크기 결정

`segments.kernels` 를 **문턱의 절반 이하**로. A6000 은 문턱 ~1,200 → 500
(42 %). 그 지점에서 `a` 증가는 측정 한계 이하였다.

재시작 오버헤드를 확인한다.

```bash
python3 scripts/rehearse.py --list-segments --json
python3 scripts/sweep.py --dry-run
```

재시작 오버헤드가 5 % 를 넘으면 세그먼트를 키워 문턱에 더 가깝게 간다.
5 % 이하면 그대로 둔다 — **여유를 남기는 쪽이 낫다.**

## G-6. 소규모 리허설

커널을 빌드하고 짧게 돌려 정합성을 본다.

```bash
python3 scripts/build_kernels.py --align a888,a448 --jobs <N>
python3 scripts/check_smem.py && python3 scripts/smoke_splitk.py
python3 scripts/validate_constraints.py
python3 scripts/rehearse.py --all --max-jobs 2000
```

여기서 보는 것은 성능이 아니라 **하네스가 이 GPU 에서 말이 되는가**다.
smem 한계, 레지스터 한계, split-k 동작, 커널 필터가 축을 통째로 죽이지
않는지.

## G-7. ⛔ 재현성 검증 — 3 시간

전수와 **같은 코드 경로**로 짧게 돌린다. 여기서 도는 것이 전수에서 도는
것과 달라지는 순간 이 게이트는 의미가 없다.

```bash
python3 scripts/sweep.py --max-rounds 4
python3 scripts/check_anchors.py; echo "exit=$?"
```

`check_anchors.py` 가 exit 0 이어야 한다. 판정은 **절대 기준이 아니라
노이즈 대비**다 (`core/anchors.py`):

* 짧은 앵커의 `sB/sW` ≤ 1.5 — 세그먼트 간 계통 오차가 없다
* 라운드에 따른 단조 증가 없음 — 세그먼트 밖에 다른 누적이 없다
* 라운드 간 절대값 이동이 바닥 이내 — **전체가 함께** 드리프트하지 않는다

> 셋째 검사를 특히 보라. 세그먼트 간 편차만 보면 "모든 세그먼트가 똑같이
> 나빠지는" 상황이 **편차 0 으로 보인다.** A6000 에서 이 검사가 라운드
> 매핑 버그로 33 시간 내내 죽어 있었는데 오류는 하나도 안 났다 (R-6).

`sW` 열과 `모델` 열을 대조하라. `모델` 은 `core/noise.py` 가 예측하는
노이즈 바닥이고 A6000 계수로 되어 있다. **새 GPU 에서 크게 어긋나면 계수를
다시 뽑아야 한다** — 그 계수가 `answer_set()` 의 동점 판정에 쓰인다.

## 새 GPU 에서 다시 봐야 하는 것 (측정과 별개)

* **노이즈 계수** — `core/noise.py` 의 `0.000374 / t + 0.00044` 는 A6000
  앵커에서 나왔다. G-7 에서 어긋나면 다시 뽑는다.
* **형상 그리드** — 층별 난이도를 보고 조정 (`docs/next_campaign.md` 2 절).
  층 B(K 변화)가 형상 수 대비 어려운 형상을 가장 많이 공급한다.
* **드라이버 버전** — 컨테이너로 통일할 수 없다. `libcuda.so.1` 은 호스트에서
  온다. GPU 간 비교에서 남는 변수이므로 `env.json` 의 `driver_version` 을
  반드시 함께 본다.
* **일정** — GPU 성능이 아니라 **작업 수**로 잡는다. 작업당 벽시계의 3 분의
  1 은 호스트 측 고정 비용이라 1.6 배 빠른 GPU 도 25 % 단축에 그친다.
