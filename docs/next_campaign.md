# 본 캠페인 계획서 — 컨테이너 / CUDA 13.3

> 첫 A6000 33 시간 측정(CUDA 12.4, 호스트)은 **파이프라인 검증용**이었다.
> 그 데이터는 `kernelRule` 개발에 쓰고, **본 캠페인은 전부 컨테이너 안에서
> 새로 측정한다.** 두 데이터의 절대 시간을 섞지 마라 — `env_hash` 가 다르고,
> 그것이 다르다는 것이 바로 섞으면 안 된다는 뜻이다.

12.4 이미지는 만들지 않는다. 호스트-12.4 와 컨테이너-13.3 은 **두 변수가
동시에 바뀌어** 비교가 성립하지 않는다. 툴체인 민감도가 궁금하면 나중에
컨테이너 안에서 CUDA 버전만 바꿔 재는 것이 깨끗하다.

---

## 1. 환경 (고정)

| | |
|---|---|
| 이미지 | `kerneltab:cu133-*` (`docker/build.sh` 가 태그를 만든다) |
| 베이스 | `nvidia/cuda:13.3.1-devel-ubuntu22.04` @ `sha256:c13e0118...` |
| nvcc | **13.3.73** — `env_hash_v2` 의 입력이다 |
| CUTLASS | **v4.7.0** (`dcf215af...`) — 4.7.0 이 CUDA 13.3 을 지목한다 |
| Python | 3.10.12 (ubuntu22.04) |
| 커널 모드 드라이버 | 호스트 (기록만 한다. 통일 불가) |
| 유저 모드 libcuda | **이미지** (forward-compat 610.43.02) |

> 유저 모드 드라이버가 이미지에 들어 있다는 것이 A6000 검증에서 나온
> 새 사실이다. GPU 간 비교에서 **변수가 하나 줄었다.**
>
> ⚠️ **다만 공짜가 아니다.** 같은 컨테이너에서 `libcuda` 만 바꿔 교대로
> 25 회씩 재보니 compat 이 런치 오버헤드를 **+53.5 ns (+3.01 %)** 늘린다
> (U=579/625). 가장 짧은 커널 14 us 기준 **0.36 %** 로 노이즈 바닥(3.1 %)의
> 1/9 이라 측정에는 영향이 없지만, **런치당 상수**라는 점이 중요하다 —
> 드리프트가 사는 바로 그 자리다.
>
> compat 을 끄지 않는다. 끄면 유저 모드가 다시 호스트마다 달라진다.
> `cuda.driver_user_mode` 가 `env_hash` 에 들어가므로 compat 이 끼는
> 호스트와 안 끼는 호스트는 **자동으로 다른 `env_hash`** 를 받는다.
> 자세한 것은 `docs/container.md` 4 절.

## 2. 순서

각 GPU 에서 `docs/new_environment_checklist.md` 의 게이트 8 개를 통과한 뒤 전수를
켠다. ⛔ 표시된 G-4(드리프트 3 값)와 G-7(재현성)은 통과 못 하면 시작하지
않는다.

```
A6000  ->  4090  ->  H100  ->  (Blackwell)
```

**Blackwell 은 별도 캠페인이다.** CUDA 12.8+ 가 필요하므로 이미지를 올려야
하고, 그러면 `env_hash` 가 바뀌어 **전체 재측정**이다. 이전이 아니다.

## 3. 형상 그리드

전수 결과의 층별 난이도(= 중앙값 시간 / 최적 시간).

| 층 | 형상 | 난이도 중앙 | 최소 | 최대 | 난이도>2.0 |
|---|---:|---:|---:|---:|---:|
| **b_kvary** | **12** | **1.87** | 1.37 | 2.95 | **4** |
| e_square | 5 | 1.82 | 1.74 | 2.12 | 1 |
| c_waves | 11 | 1.68 | 1.55 | 1.74 | 0 |
| d_alignment | 5 | 1.67 | 1.54 | 1.95 | 0 |
| a_workload | 40 | 1.57 | 1.12 | 1.96 | 0 |

**층 B 는 형상이 층 A 의 3 분의 1 인데 난이도 2.0 초과 5 개 중 4 개를
공급한다.** 난이도가 `log K` 와 **r = −0.712** 로 상관되는 것과 일관된다 —
K 가 크면 A/B 읽기가 지배하고 대역폭이 포화되어 config 가 바꿀 수 있는
재사용 패턴에 여지가 없다.

조정:

* **층 B 12 → 20 개.** `K < 1024` 구간을 촘촘히. 가장 어려운 형상 상위
  둘이 `1024x4096x256`, `1024x4096x128` 로 둘 다 여기다.
* **층 A 의 M 을 10 → 7 개로.** 난이도가 가장 낮고(1.57) 중복이 많다.

> ⛔ **층 A 를 너무 줄이지 마라.** 실무 워크로드 대표성이 층 A 의 존재
> 이유이고, **"쉬운 형상이 많다" 는 것 자체가 보고할 사실**이다. 난이도만
> 보고 설계하면 실제 분포를 왜곡한다. 규칙이 "여기서는 아무거나 골라도
> 된다" 를 배우는 것도 결과의 일부다.

## 4. config 축 — ★ **판정 기준을 고쳤다**

전수 결과에서 **답이 정해져 있는 축**은 열거에서 고정한다. 축이 무의미한
것이 아니라 답이 하나라는 뜻이고, 그런 축을 남기면 측정 시간만 쓴다.

> ### ⚠️ "최적 0회" 가 아니라 **"정답 집합에 0회"** 로 잰다
>
> 노이즈 바닥을 도입한 뒤로 "최적을 낸 횟수" 는 너무 약한 기준이 됐다.
> 어떤 값이 **한 번도 1등은 아니지만 66 형상 중 10 곳에서 1등과 구분
> 불가능**할 수 있다. 그것을 빼면 그 10 형상에서 동점 최적 하나를 잃는다.
>
> 정답 집합 = 최적 대비 `2 x noise_floor` 이내
> (`core/table.py::answer_set`, 분해능 항 포함).
>
> **이 기준으로 다시 재니 후보 6 개 중 3 개가 뒤집혔다.**

| 후보 | 행 수 | 최적 횟수 (12.4 / 13.3) | **정답 집합** (12.4 / 13.3) | 결정 |
|---|---:|---:|---:|---|
| `warp_m = 128` | 47,052 | 0 / 0 | **0 / 0** | ⛔ **제외** |
| 스필 발생 warp tile | 66,459 | 0 / 0 | **0 / 0** | ⛔ **제외** |
| tile `256x256` | 7,817 | 0 / 0 | **0 / 0** | ⛔ **제외** |
| `warp_k` 분할 | 102,002 | 0 / 0 | **10 / 11** | ✅ **남긴다** (뒤집힘) |
| `split_k_mode = parallel` | 407,465 | 0 / 0 | **2 / 1** | ✅ **남긴다** (뒤집힘) |
| `stages = 8` | 45,221 | 0 / 0 | **10 / 10** | ✅ **남긴다** (뒤집힘) |
| `stages = 2` | 271,660 | 2 / 2 | 9 / 11 | ✅ 남긴다 |

**제외로 확정된 셋은 121,328 행** (전체의 13.8 %)이고, 두 캠페인 모두에서
정답 집합에 **한 번도** 들어가지 않았다.

> `warp_m=128` 은 물리적 근거도 있다 — warp tile `(128,64)` 는 빌드에서
> **120/120 = 100 % 스필**이다. "스필 발생" 과 겹치는 축이다.

### 뒤집힌 셋을 남기는 이유

`warp_k` 분할·`parallel`·`stages=8` 은 **한 번도 1 등이 아니었지만**
1~11 형상에서 1 등과 **구분되지 않는다.** 빼면 그 형상들에서 동점 최적
하나가 사라지고, 규칙이 고를 수 있는 폭이 줄어든다.

특히 `split_k parallel` 은 40 만 행(46 %)을 쓴다. 그래도 빼지 않는 이유:

* 정답 집합에 12.4 에서 2 형상, 13.3 에서 1 형상이 있다 — **0 이 아니다.**
* `serial` 과 부분합 누적 경로가 달라 L2 크기와 원자적 누적 성능이 다른
  GPU 에서 뒤집힐 수 있다.

**중단 조건:** 4090 에서도 **정답 집합에 0 형상**이면 그때 뺀다. 두 GPU 에서
0 이면 근거가 충분하다. "최적 0회" 로는 판단하지 않는다.

### ⛔ 성능으로 config 를 거르지 마라

위 결정은 전부 "이 축의 답이 하나였다" 는 관찰이지 "느린 것을 뺀다" 가
아니다. 특히 `SPLIT_K` 에서 3, 6, 12 를 빼지 마라 — `waves < 1` 형상의
가설 검정에 필요하고, 실제로 `split_k=3` 이 66 형상 중 **16~17 회 최적**,
정답 집합에는 **21~25 형상**에 들어간다. 3 의 배수 기각은 "3 이 특별하지
않다" 는 뜻이지 "3 이 나쁘다" 가 아니다.

### ★ 축 덮개 — **빼는 것만 보지 말고 없는 것도 봐라**

위 표는 전부 "무엇을 뺄까" 다. 반대 방향은 아무도 안 봤다 — **우리 축에
아예 없는 값**이다. 캠페인 **전에** 한 번 돌린다:

```bash
python3 scripts/check_axis_coverage.py --vendor <vendor.json>
```

벤더 추천 582 개 중 **35 개(6.0 %)가 우리 공간 밖**이었다. regret 점수에는
"가장 가까운 config" 로 대체돼 들어가므로 **점수만 보면 안 보인다.**
자세한 것은 [`axis_coverage.md`](axis_coverage.md).

| 값 | 추천 | 판정 | 이번 캠페인 |
|---|---:|---|---|
| `split_k = 5` | 18회 / 7형상 | ★ **진짜 구멍** (58/66 형상에서 유효) | 아래 결정 |
| `warp_tile = (128,32)` | 2회 / 2형상 | ★ **진짜 구멍** (3개 tb tile 에서 유효) | 아래 결정 |
| `stages = 1` | 15회 / 3형상 | 남의 공간 — **CUTLASS 2.x 에서 수치가 틀린다** | 넣지 않는다 |

> `stages=1` 은 `nvcc` 도 통과하고 `can_implement()` 도 `kSuccess` 를
> 돌려주는데 결과가 **65,536 원소 중 62,674 개 틀린다.** 우리 열거기의
> `explain_kernel` 도 `valid` 로 판정한다 — **`STAGES` 목록에 1 이 없다는
> 것이 유일한 방어였다.** 유효성 검사가 아니라 축 목록이 막고 있었다.

**결정이 필요하다 (비용이 있다):**

| 추가 | 격자 증가 | 판단 근거 |
|---|---|---|
| `split_k = 5` | 런타임 config **+12.5 %** (커널 재빌드 없음) | 5 를 뺀 것은 의도가 아니라 **누락**이다. 3·6·12 는 SM 84=2²·3·7 가설로 넣었고 5 는 그 가설에도 2의 거듭제곱에도 안 들어가 아무도 안 물었다. `split_k=3` 이 정답 집합 21~25 형상에 드는 것을 보면 비 2-거듭제곱이 죽은 축이 아니다 |
| `warp_tile = (128,32)` | 커널 수 증가 (빌드 시간) | `warp_m=128` 을 제외하기로 했는데 그 근거는 `(128,64)` 의 **100 % 스필**이다. `(128,32)` 는 누산기가 절반이라 스필 양상이 다를 수 있다 — **같은 축이라고 묶어 지우면 안 된다.** 먼저 표본 20개를 빌드해 스필률을 본다 |

**권고:** `split_k=5` 는 넣는다 (재빌드 불필요, 근거가 누락이다).
`warp_tile=(128,32)` 는 **빌드 표본으로 스필률만 먼저 확인**하고,
`(128,64)` 처럼 100 % 스필이면 넣지 않는다.

## 5. 프로토콜 — 워밍업 시간 예산화 ⭐ **최우선 변경**

`min_warmup = 10` 이라 느린 커널은 워밍업만 자기 실행시간의 10 배를 쓴다.
캠페인 전체(886,471 작업)에서 계산하면:

| | |
|---|---|
| 워밍업 GPU 시간 | **27,560 s** |
| 측정 GPU 시간 | 25,362 s |
| **워밍업 비중** | **52.1 %** |
| 작업당 비율 (중앙 / 평균) | 24.4 % / 33.3 % |

**워밍업이 측정보다 GPU 시간을 더 썼다.** 작업당 중앙값이 24 % 인데 전체
비중이 52 % 인 이유는 느린 꼬리다 — 프로토콜 시간이 p50 26 ms, p90 132 ms,
p99 491 ms 로 느린 작업이 총합을 지배한다.

→ 워밍업을 반복 횟수가 아니라 **시간 예산**으로 바꾼다
(`min_warmup` → `min_warmup_ms`). 측정 조건이라 `env_hash` 가 바뀌지만
**새 캠페인이므로 상관없다** — 12.4 캠페인 중에는 조건 변경 불가라
미뤄뒀던 항목이다.

**절약 규모가 캠페인 전체의 30~40 % 다.** 형상 그리드 조정보다 우선한다.

### ⛔ 바꾼 뒤 반드시 검증할 것

워밍업을 줄이는 것은 **측정값을 직접 바꿀 수 있는 변경**이다. 세 가지를
확인하기 전에는 전수를 켜지 않는다.

| # | 무엇 | 기준 | 왜 |
|---|---|---|---|
| 1 | 첫 측정이 냉시작이 아닌가 | 워밍업 유/무의 차이가 노이즈 바닥 이내 | A6000 에서 워밍업 없이 재면 4096³ 이 **+26.32 %** 였다 |
| 2 | 앵커의 슬라이스 start → end 이동 | **1 % 이내** | 세그먼트마다 프로세스를 새로 띄우므로 매번 냉시작이다. 여기가 무너지면 전 구간이 오염된다 |
| 3 | 최소 워밍업 시간의 **하한** | 하한을 반드시 둘 것 | 리허설 실측에서 **20 초**로 충분했다 (265 회, 종료 시 1350 MHz / 7601 MHz / 55 ℃) |

> 1 번은 `--no-soak` 로 소킹을 껐을 때 워밍업이 통째로 사라졌던 사고와
> 같은 자리다 (`WARMUP_SECONDS` 가 정의만 되고 안 쓰였다). 그때 로그는
> "워밍업만 한다" 를 찍고 있었다. **로그를 믿지 말고 값을 확인하라.**

### 실측 절감 (리허설 1,520 작업 + 캠페인 분포 모델)

모델을 리허설 실측과 대조했더니 **오차 +0.3 %** 라 캠페인 투영을 믿을 수 있다.

| | 옛 | 새 | 절감 |
|---|---:|---:|---:|
| 오버헤드 (캠페인 886,471 작업) | 54,401 s | 21,339 s | **60.8 %** |
| 측정 | 25,362 s | 25,362 s | — |
| **GPU 합계** | 79,763 s | 46,701 s | **41.5 %** |

```
12.4 실제   벽시계 33.0h = GPU 22.2h + 호스트 10.8h
새 프로토콜        = GPU 13.0h + 호스트 10.8h = **23.8h**
-> 벽시계 28% 단축
```

> **GPU 시간은 41.5 %, 벽시계는 28 %** 다. 호스트 고정 비용 10.8 시간은
> 줄지 않는다. 일정은 GPU 성능이 아니라 **작업 수**로 잡는다 —
> 4090 이 1.6 배 빨라도 25 % 단축에 그친다.

### 향후 개선 — 호스트 측 비용 (⛔ 이번 캠페인에서는 손대지 마라)

워밍업을 줄이고 나면 **호스트 10.8 시간이 전체의 45 %** 가 된다. 다음
최적화 대상은 거기다: 동기화, ctypes 호출, JSON 기록.

⛔ **이번 캠페인 중에는 건드리지 마라.** 측정 조건을 또 바꾸면 `env_hash` 가
바뀌고 G-7 을 처음부터 다시 돌려야 한다. 다음 캠페인 준비 때 볼 것.

### 캠페인이 끝나면 정리할 것 (측정 중 금지)

| | 무엇 | 왜 |
|---|---|---|
| 1 | 호스트 측 비용 (위) | 이제 전체의 45 % |
| 2 | `rehearse.py` 의 가드 생략을 **예외로 구현한 것** | 전수 모드에서 `raise RuntimeError("전수 모드에서는 생략")` 을 던지고 로그에 **"가드 검증 중 예외"** 로 찍힌다. 의도한 생략인데 사고처럼 보인다 — 이 저장소가 싫어하는 "로그가 사실과 다른" 경우다. 동작은 정상 |
| 3 | `check_smem.py` 의 역할 재정의 | `validate_constraints` 가 183 배 넓은 범위로 같은 것을 검증한다. GPU 없이 **빌드 전에** 돌 수 있다는 것이 유일한 차별점이므로 그렇게 문서화하거나 지운다 |

## 6. 세그먼트 크기 — **CUDA 13.3 에서 다시 쟀다**

⛔ **A6000 / CUDA 12.4 값을 그대로 쓰면 안 된다는 것이 실측으로 확인됐다.**

| | A6000 / CUDA 12.4 | A6000 / **CUDA 13.3** |
|---|---:|---:|
| 문턱 | 1,154 모듈 | **962 / 1,051** (두 번 측정) |
| 문턱 위 기울기 | 77.4 us/1,000 | **50.6 / 69.6 us/1,000** |
| 기준선 `a` | 16.7 us | 18.4 us |
| 왜곡 배율 | 243 배 | 153 / 310 배 |
| `b` 변화 | −3.42 % | −0.31 / −3.12 % |
| **권장 `segments.kernels`** | 461 | **420** |

> **두 번 쟀고 문턱이 962 와 1,051 로 나왔다.** `STEP=100` 의 ±1 스텝이므로
> 해상도 안이지만, 그 사실 자체를 `drift_profile.json` 의 `history` 에
> 남긴다 — 4090 에서 이보다 크게 흔들리면 `--step 50` 으로 줄여야 한다는
> 신호다. 채택한 420 은 **낮은 쪽 문턱(962) 기준으로도 43.7 %** 라 안전하다.

**드리프트는 CUDA 13.3 에서도 그대로 있다.** 문턱이 낮아지고(1,154 → 962)
기울기는 완만해졌다(77 → 51 us/1,000). 즉 **CUDA 13 이 이 문제를 고치지
않았다** — 대책이 여전히 필요하고, 세그먼트는 **더 작게** 잡아야 한다.

12.4 캠페인에서 쓴 500 을 그대로 옮겼다면 문턱의 **52 %** 가 되어 여유가
거의 사라진다. **420** 으로 간다 (두 번째 측정의 문턱 1,051 × 40 %).

```bash
kerneltab drift --gpu <UUID> --max-touch 3000 --step 100
#   -> results/drift_profile.json 의 recommended_segment_kernels
```

`phase0_env.py` 가 이 값을 **자동으로** 읽어 `segments.kernels` 에 넣는다
(툴체인이 같은 프로파일만). 사람이 옮겨 적게 하면 안 옮긴다.

> 측정 조건 차이를 밝혀 둔다. 12.4 쪽은 커널 7,230 개 풀에서 3,000 개를
> 터치했고(성공 2,629), 13.3 쪽은 a888/a448 만 빌드한 2,210 개 풀에서
> 2,000 개를 터치했다(성공 1,767). 무릎은 두 범위 모두 안쪽에 있으므로
> 문턱 판정에는 영향이 없지만, 기울기는 표본이 다르므로 정밀 비교로 쓰지
> 마라. **4090 에서는 전수 빌드 후 다시 잰다.**

`measure_drift.py` 자체는 A6000/12.4 에서 **원래 알던 값을 재현**해 검증했다
(문턱 1,154 vs ~1,200, 기울기 77.4 vs ~75 us/1,000).

## 7. 여러 GPU 를 동시에 쓸 계획이면

빠른 GPU 한 대보다 여러 대 병렬이 낫다. 각 GPU 는 자기 `env_hash` 로
독립적으로 돌고 번들이 조건을 들고 다니므로 합치는 데 문제가 없다.

**다만 같은 서버라면 간섭 실험을 먼저 하라.** PCIe / 호스트 메모리 / CPU 를
공유하고, 측정 루프의 3 분의 1 이 호스트 측 비용이라 특히 그렇다.

## 8. 호스트 요구사항

| | |
|---|---|
| `nvidia-container-toolkit` | 필수 (`--gpus` 동작 조건) |
| 호스트 드라이버 | r580 이상에서 확인 (CUDA 13 요구). **forward-compat 로 도는 것**이라 더 낮으면 확인 필요 |
| RAM | 병렬 nvcc 16~24 job 이면 수십 GB. `--memory` 제한 **금지** |
| CPU | `--cpus` 제한 **금지** — 측정 루프의 1/3 이 호스트 측 비용이다 |
| 클럭 고정 | **호스트에서** 한다. 컨테이너 안에서는 불가능하고 `--privileged` 로 뚫지 마라 |
| 볼륨 | `-v <경로>:/data` 로 **통째로** 마운트. 하위 경로를 따로 마운트하지 마라 |
| 사용자 | **항상** `--user $(id -u):$(id -g)`. root 로 돌리면 볼륨 권한 문제와 `cutlass.commit=null` 이 **둘 다 숨는다** |

> forward-compat 는 NVIDIA 가 공식적으로는 **데이터센터 GPU** 대상으로
> 지원한다. A6000(워크스테이션)에서 동작을 실측했지만 보장은 아니다.
> **클라우드 4090 인스턴스의 드라이버를 먼저 확인할 것.**
