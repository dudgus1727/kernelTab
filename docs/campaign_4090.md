# RTX 4090 캠페인 — 조건 기록 (진행 중)

> **앞선 4090 시도는 측정 문제가 아니라 서버를 더 쓸 수 없어 중단됐다.**
> 새 호스트에서 게이트부터 다시 한다. **앞선 시도의 데이터는 이 저장소에
> 없다** — 커밋도 번들도 남아 있지 않다. 그래서 섞일 표가 없고, 앞선 값은
> "그 시도의 보고(데이터 없음)" 로만 인용한다.

측정 중에는 이 문서를 고치지 않는다. 관측한 것은 "캠페인 중 관측" 에만 덧붙인다.

### ★ 드라이버가 앞선 시도(580.95.05)와 다르다 — 손실이 아니다

게이트 중 `apt-get install nvidia-container-toolkit` 이 드라이버 스택을 함께
올렸다 (580.95.05 → 580.173.02). 배포판이 옛 버전을 교체해 되돌릴 수 없고,
커널 모듈을 재로드해 **양쪽을 580.173.02 로 일치**시켰다.

**맞출 이유가 없다.** `env_hash` 의 목적은 *다른 조건을 한 표에 섞지 마라*
이지 *앞선 캠페인과 같게 하라* 가 아니다. 그리고 앞선 4090 데이터가 없으므로
섞일 표 자체가 없다. **이것이 이 캠페인의 조건이고, 기록하면 끝난다.**

절차는 `docs/new_environment_checklist.md` G-0 에 넣었다 — 게이트 중에는
무해하고 **측정 중에는 치명적**이다.

### G-1/G-2 — 고정값을 2400 으로 정한 이유

미고정 실부하(`rehearse` 1,920 작업, 2.2 분)에서:

```
pstate   P2      SM 중앙 2745  최소 2565  최대 2760
메모리   10251 MHz (P0 는 10501)      전력 중앙 334 W / 최대 381 W (상한 450)
온도     41 -> 75 °C (2.2 분 만에)
```

| 후보 | 관측 하한 2565 대비 | 실효 피크 | ridge |
|---:|---:|---:|---:|
| 2520 (정격 부스트) | −1.8 % | 165.2 | 167.9 |
| **2400** | **−6.4 %** | **157.33** | **159.9** |
| 2250 | −12.3 % | 147.5 | 149.9 |

**2520 은 여유가 1.8 % 뿐이다.** 관찰 창이 2.2 분인데 그 사이 온도가 이미
34 °C 올랐다. 20 시간 캠페인은 더 뜨겁고 더 무거운 구간이 있다 — 5090 이
"20분 soak 294~389 W vs 실제 캠페인 중앙 434 W" 로 밟은 자리다.

**낮추는 비용은 사실상 0 이다.** 시간 예산 프로토콜이라 작업당 GPU 시간
상한이 클럭과 무관하게 45 ms 다 (`decisions.md` 20). 캠페인 길이는 작업 수가
정한다.

고정 후 4 분 실부하 검증:

```
clocks.sm    min=max=mean=median 2400 MHz,  목표 이상 유지 240/240 = 100.0%
clocks.mem   median 10251 (부하 중 P2)
power        최대 285.8 W / 450 W = 64%
temp         45 -> 70 °C
throttle     gpu_idle 1s 만.  sw_power_cap 0.0%
time_ms      첫 1/4 2.9071 -> 마지막 1/4 2.9087 = +0.05%,  전체 변동폭 0.74%
```

### ★ `-lmc` 를 걸어도 부하 중에는 P2 로 내려간다

`SUPPORTED_CLOCKS` 는 메모리를 **10501 하나만** 노출하는데, 컴퓨트 워크로드는
P2 로 동작해 **10251 MHz** 다. 고정의 효과는 "유휴 405 ↔ 부하 10251" 이
"유휴 10501 ↔ 부하 10251" 로 바뀌는 것이다. A6000(요청 8001 / 실측 7601)과
같은 현상이고 폭은 훨씬 작다 (97.6 %).

`locked_mem_mhz` 에는 **부하 중 실측 10251** 을 넣는다. 이 보정을 빼면
ridge point 의 분모가 2.4 % 틀린다.

### ridge 가 A6000 과 거의 같다

```
A6000   116.1 / 729.7  = 159.1
★ 4090  157.33 / 984.1 = 159.9      (2400 MHz 고정)
5090    208.194 / 1766.5 = 117.9
```

**4090↔A6000 사이에서는 `is_memory_bound` 가 거의 안 뒤집히고, 5090 과는
크게 갈린다.** 공통 형상에서 실제 개수를 세어 여기 적을 것.

### G-3 — 실측

#### 실효 피크: `mma.sync` 로 FP32 누산 반감을 확정했다

```
FP32 누산  156.73 TFLOP/s   -> 128 SM x 2 flop x 2.4 GHz 로 역산 255.1 FMA/clk/SM  -> 256
FP16 누산  309.57 TFLOP/s   ->                              역산 503.9            -> 512
비율 1.9752
```

**`known.json` 의 `fma_f16_per_clk_per_sm = 256` 이 실측으로 확정됐다.**
이 항목의 `source` 산문은 2026-09-02 까지 512 로 적혀 있어 값(165.2)의 2 배를
내고 있었다 — 값이 옳고 산문이 틀렸다. 이제 `peak_derivation` 이 구조화된
형태로 들어 있고 `tests/test_hwspec.py` 가 대조한다.

```
예측 실효 피크  165.2 x 2400/2520 = 157.333 TFLOP/s
실측                              156.73     (예측의 99.6 %)
```

#### 눈금 = **32 ns** — 여섯 길이에서 전부 일치

`tools/tick_probe.cu` (spin 커널, 목표 2 us ~ 2 ms 여섯 구간 x 800 회) +
`tools/tick_report.py`.

| 후보 | 설명력 | 홀수 배수 | 판정 |
|---:|---:|---:|---|
| 16 ns | 100 % | **0.0 %** | ⛔ 기각 — 진짜 눈금의 짝수배다 |
| **32 ns** | **100 %** | 38~52 % | ★ 채택 |
| 64 ns 이상 | 55~61 % 이하 | — | 설명력 미달 |

**5090 의 32 → 16 정정을 반복하지 않았다.** 그때는 홀수 배수 검사가 없었다.

```
A6000 1024 ns   /   ★ 4090 32 ns   /   5090 16 ns   /   H100 32 ns
```

#### SOL — 문턱 아래 **0 개**, 최소 여유 592 %

문턱 = 3 x `launch_bracketed_grid`(3.072 us) = **9.216 us**.

| 층 | 형상 | SOL | 문턱 대비 |
|---|---|---:|---:|
| a_workload / c_waves | `256x4096x4096` | 54.60 us | 592 % |
| b_kvary | `4096x4096x256` | 54.60 us | 592 % |
| b_kvary | `8192x4096x128` | 71.39 us | 775 % |

**가장 나쁜 구간(문턱의 70~90 %)에 걸친 형상이 하나도 없다.** 앵커
(`DRIFT_SHAPES` 2048³/4096³)도 함께 봤다 — 둘 다 문턱의 수십 배다.

#### forward-compat — **+1.4~2.1 %**, 브래킷 측정에는 영향 없음

같은 컨테이너에서 `libcuda` 만 바꿔 **교대로** 25 회씩 (compat 610.43.02 vs
호스트 native 580.173.02).

| 항목 | compat | native | 차이 | U (중심 312) |
|---|---:|---:|---:|---:|
| `launch_async_small` | 2.0188 us | 1.9775 us | **+41.3 ns (+2.09 %)** | 533 |
| `launch_async_grid` | 2.0026 | 1.9747 | +27.9 ns (+1.42 %) | 483 |
| `launch_bracketed_small` | 2.3360 | 2.3040 | +32.0 ns (눈금 한 칸) | **308 — 겹침** |
| `launch_bracketed_grid` | 3.0720 | 3.0720 | 0.0 | **312 — 동일** |

```
A6000   +53.5 ns (+3.01 %)   느려진다
★ 4090  +41.3 ns (+2.09 %)   느려진다 (A6000 과 같은 방향·크기)
5090    -167 ns  (-9.1 %)    빨라진다
```

**하네스가 실제로 쓰는 브래킷 측정에서는 차이가 없다** (U 가 중심값이다).
유지한다 — 끄면 유저 모드가 다시 호스트마다 달라진다.

## 앞선 시도의 값 — **참고용, 데이터 없음**

| | 앞선 시도의 보고 | 이번 실측 |
|---|---|---|
| SM 클럭 고정 | 2400 | **2400** |
| ridge | 159.9 | **159.9** |
| 드리프트 문턱 | 1,394 | (G-4) |
| 문턱 위 기울기 | 158.5 us/1k | (G-4) |
| 눈금 | 32 ns | **32 ns** ★ 일치 |
| `high_outlier_frac` | 8.4 % | 9.4 % (미고정 리허설, 옛 그리드) |

**출처는 앞선 시도의 보고이며 데이터가 남아 있지 않다.** 목표가 아니라 감이다.
클럭과 ridge 가 같은 값에 떨어졌지만, 이번 값은 이 카드의 관측 하한
(2565 MHz)에서 독립적으로 유도한 것이다.
