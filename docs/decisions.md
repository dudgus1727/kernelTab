# 스펙 대비 변경한 것

원 스펙에서 벗어난 결정과 **그 근거**. 각 항목은 "무엇을 바꿨나" 가 아니라
"바꾸지 않았으면 무엇이 틀렸을 것인가" 를 적는다. 근거가 없으면 그것은
결정이 아니라 취향이다.

되돌리기 전에 반드시 읽을 것 — 대부분은 CUTLASS 소스나 실측으로 확인한
것이며, 되돌리면 조용히 틀린 숫자가 나온다.

설계 원칙 자체는 README 의 "설계 결정과 그 이유" 에 있다.

---


원래 지시와 다르게 구현한 부분과 근거. 되돌릴 수 있게 남긴다.

## 1. `EpilogueOutputOp` 의 ScaleType: `NoBetaScaling` → `Default` (+ 런타임 beta=0)

지시는 `ScaleType::NoBetaScaling` 이었고 이유는 "beta=0 이므로 C 를 읽지 않아
더 빠르다" 였다. 그런데 CUTLASS 소스에서 그 enum 은 정반대로 동작한다
(`epilogue/thread/scale_type.h`, `linear_combination.h`):

| ScaleType | 계산식 | `is_source_needed()` |
|---|---|---|
| `Default` | `D = α·Acc + β·C` | `β != 0` |
| `NoBetaScaling` | `D = α·Acc + C` | **항상 true** (C 를 읽는다) |
| `OnlyAlphaScaling` | `D = α·Acc` | **항상 false** |

* `NoBetaScaling` 은 partition 0 에서도 C 를 읽으므로 원래 목표에 반한다.
* `OnlyAlphaScaling` 은 source 를 영원히 읽지 않는다. serial split-K 는
  partition > 0 에서 `set_k_partition()` 이 β=1 로 바꿔 이전 부분합을 다시
  읽어 누적하는데, 이 경로가 죽어서 **결과가 조용히 틀린다.**
* `Default` + 런타임 β=0 이면 partition 0 에서 `is_source_needed()==false` 라
  C 를 읽지 않고(목표 달성), partition > 0 에서는 β=1 이 되어 serial split-K
  가 정상 동작한다.

즉 지시의 *의도*(β=0, C 안 읽기)는 그대로 지키고 enum 만 바꿨다.

`LinearCombination` 의 `Count` 인자는 `align_c` 로 준다. 이것이 C/D 의 벡터
접근 폭을 결정하므로 alignment 가 8 미만인 형상에서 8 로 두면 잘못된 메모리
접근이 된다.

## 2. `is_valid_runtime` 규칙 1: `K % (split_k · tile_k) == 0` → 실효 split_k 일치

원래 규칙을 그대로 쓰면 지시의 다른 두 요구가 **동시에 불가능해진다.**

* 그리드의 어떤 K 도 3 으로 나누어떨어지지 않는다 (4096, 11008, 2의 거듭제곱,
  512, 4100, 4098, 4097). 따라서 `split_k ∈ {3, 6, 12}` 는 **단 한 번도 측정될
  수 없다** — 명시적으로 검증하라고 한 가설이 검증 불가능해진다.
* 층 D 와 리허설 형상 `(1024, 4096, 4100)` 은 `4100 % 32 ≠ 0` 이라 split_k=1
  조차 통과하지 못해 **유효 조합이 0 개**가 된다. alignment=4 경로를 검증할 수
  없다.

CUTLASS 는 애초에 K 가 나누어떨어지지 않아도 알아서 자른다
(`kernel/params_universal_base.h : init_grid_tiled_shape()`):

```
kAlignK   = max(8, (A row-major or B col-major) and K % 64 == 0 ? 64 : 1)
gemm_k_size          = round_up(ceil_div(K, split_k), kAlignK)
grid_tiled_shape.k() = ceil_div(K, gemm_k_size)      <- 실제 슬라이스 수
```

진짜 위험은 나누어떨어지지 않는 것이 아니라 **요청한 split_k 와 실제 슬라이스
수가 다른 것**이다. 예를 들어 K=512 에 split_k=12 를 요청하면 실제로는 8 개가
만들어져, 8 과 12 라는 다른 이름으로 같은 것을 두 번 재게 된다. 그래서 규칙을
이렇게 바꿨다.

```python
rc.split_k * cfg.tile_k <= p.K            # 슬라이스가 최소 K 타일 하나는 담아야
effective_split_k(p, rc) == rc.split_k    # 요청 == CUTLASS 가 실제로 만드는 수
```

지시가 든 예시 `(1024, 4096, 512)` 에서 이 조건이 실제로 거르는 것은 그대로다
(split_k=6/12/16 탈락). `(1024, 4096, 4100)` 은 15 개 런타임 config 를 얻는다.

## 3. 탐색 축 확대: `warp_count ∈ {4,8}` → `{4,8,16}`, 누산기 상한 200 → 256

원래 값은 추정치였다. 레지스터 실사용량과 스필은 빌드 시 `-Xptxas -v` 로
**실측**해 `kernels.jsonl` 에 남기므로, 추정치로 미리 자르는 것보다 빌드해서
기록하는 편이 데이터로서 낫다. "성능 기준으로 거르지 마라" 원칙과도 일관된다.

부수적으로 `threads_per_block <= min(1024, hw.max_threads_per_sm)` 가드를
추가했다. warp_k 분할(PartitionsK)까지 곱하면 블록 스레드 수가 CUDA 한도를
넘을 수 있는데, 이건 런치 자체가 불가능한 조합이다.

결과: alignment 조합당 1,155 → 1,575 개.

## 4. `is_valid_kernel` 에 CUTLASS 컴파일 제약 2 개 추가

빌드해 보면 특정 조합이 `static_assert` 로 거부된다. **성능이 아니라 컴파일
가능성** 문제이므로 `is_valid_kernel` 의 본래 역할에 해당한다. 두 제약 모두
CUTLASS 소스에서 유도한 뒤 실측 1,263 개 빌드와 대조해 **오탐 0 / 미탐 0**
을 확인하고 넣었다 (`scripts/validate_constraints.py`).

**`mainloop_smem_thread_map`** — `transform/pitch_linear_thread_map.h`
```
tile_m · tile_k >= 8 · threads   and   tile_n · tile_k >= 8 · threads
```
A/B 모두 smem 에서 crosswise 레이아웃이고 smem 접근 폭은 전역 alignment 와
무관하게 128 비트 고정이라, 조건이 이렇게 단순해진다.

**`epilogue_thread_map`** — `output_tile_thread_map.h` / `predicated_tile_iterator.h`
`RowArrangement` 가 `8 > warps_n · warps_k` 로 갈리고 각 분기에서
`Iterations::kRow / kColumn` 이 0 이 되면 거부된다.

결과: alignment 조합당 1,575 → 1,365 개 (13.3% 제거). 통째로 죽는 축은 없다.

## 5. horizontal 스위즐을 직접 구현 (`measure/kt_swizzle.h`)

CUTLASS 의 `GemmHorizontalThreadblockSwizzle` 은 `get_tile_offset(GemmCoord)`
시그니처라 `get_tile_offset(int log_tile)` 로 호출하는 `kernel::GemmUniversal`
과 **컴파일되지 않는다** (구버전 `device::Gemm` 경로 전용). 그냥 빼면 커널의
20% 가 사라지고, 무엇보다 **래스터 방향 축 자체가 사라진다.** 이 축은 SM90
3.x API 의 `raster_order = along_m | along_n` 과 직접 대응하므로 여기서 잃으면
나중에 SM80 ↔ SM90 전이 실험이 성립하지 않는다.

직접 짠 코드이므로 별도로 검증했다 (`scripts/verify_swizzle.py`):

| 형상 | 타일 격자 | identity(1) | horizontal |
|---|---|---|---|
| (8192, 2048, 4096) | m=64 ≫ n=16 | 1.621 ms | **1.124 ms** |
| (2048, 8192, 4096) | m=16 ≪ n=64 | **1.119 ms** | 1.590 ms |

* grid dim 이 `(64,16) ↔ (16,64)` 로 실제로 뒤바뀌는 것을 `get_grid_shape()` 로 실측
* 네 형상 모두 `max_rel_error = 0.0` (cuBLAS 와 비트 단위 일치)
* 성능이 **대칭적으로 역전**된다 — 스위즐이 실제로 적용된다는 증거. 단순히
  "값이 다르다" 가 아니라 물리적으로 기대되는 방향으로 다르다.

## 6. split-K 부분합 정밀도 — serial 과 parallel 모두 fp16 (비대칭 아님)

**결론부터: 두 모드의 저장 정밀도는 같다. 비교 조건은 공정하다.**

CUTLASS 2.x `kernel::GemmUniversal` 에서 부분합이 어디에 어떤 타입으로
놓이는지는 이렇다.

| 모드 | 부분합 위치 | 부분합 타입 | 누산 |
|---|---|---|---|
| serial (`kGemm`, k>1) | `D` 자체 | **`ElementC` = fp16** | 파티션마다 fp32 로 더하고 fp16 으로 되씀 |
| parallel (`kGemmSplitKParallel`) | workspace | **`ElementC` = fp16** | 리덕션 커널이 fp32 로 합산 후 1 회 반올림 |

serial 이 fp32 누산기를 이어받는 것이 아니다. `kernel/gemm_universal.h` 에서

```cpp
// For subsequent threadblocks, the source matrix is held in the 'D' tensor.
if (threadblock_tile_offset.k()) {
  iterator_C = iterator_D;      // <- 이전 부분합을 D(=fp16)에서 다시 읽는다
}
```

즉 파티션 사이의 중간값이 **매번 fp16 으로 전역 메모리를 왕복**한다. 반올림
횟수도 두 모드가 비슷하며(각 슬라이스 1 회), 오히려 parallel 쪽이 마지막
합산을 fp32 로 한 번에 하므로 미세하게 유리하다.

**fp32 부분합은 왜 안 쓰는가.** 부분합 타입은 곧 커널의 `ElementC` 다
(`get_workspace_size()` 가 `sizeof(ElementC) * ...` 로 정의되고 epilogue 가
`iterator_D` 로 쓴다). fp32 부분합을 얻으려면 `ElementC = float` 인 커널을
따로 인스턴스화해야 하는데 — CUTLASS 라이브러리가
`find_gemm_operation_for_parallel_reduction()` 으로 하는 일이 정확히 그것이다 —
그러면

* `split_k_mode` 가 런타임 인자가 아니라 **빌드 축**이 되어 커널 수가 2 배가
  되고 KernelConfig / RuntimeConfig 분리의 전제가 깨진다,
* serial 쪽은 부분합이 곧 최종 출력이라 **출력 dtype 자체가 fp32 로 바뀐다.**
  그러면 epilogue 쓰기 트래픽이 2 배가 되어 split-K 를 안 쓰는 측정까지
  전부 오염된다.

그래서 fp16 으로 둔다. 대신 해석에 필요한 정보를 결과에 남긴다:
`results.jsonl` 의 `partials_dtype` (실효 split_k > 1 이면 `"f16"`) 과
`workspace_dtype` (parallel 이면 `"f16"` 부분합 버퍼, serial 이면 `"i32"`
세마포어). 이 두 필드가 없으면 나중에 정확도 분석에서 "방식의 차이" 와
"저장 정밀도의 차이" 를 구분할 수 없다.

측정 시간에는 parallel 의 리덕션 커널을 포함한다 (빼면 serial 과 비교 자체가
성립하지 않는다).

## 7. `launch_infeasible` status 추가

`cutlass::Kernel2` 에는 `__launch_bounds__` 가 없어서 ptxas 가 스레드 수에 맞춰
레지스터를 제한하지 않는다. 그 결과 `regs_per_thread × threads > regs_per_sm`
인 커널이 만들어지는데, 이건 빌드는 되지만 **런치가 불가능**하다
(`cudaOccupancyMaxActiveBlocksPerMultiprocessor` 가 0 을 돌려준다).
빌드 전에는 예측할 수 없고(레지스터는 ptxas 의 결과) 빌드 후에는 정확히
판정되므로, 측정 직전에 확인해 실행하지 않고 이 status 로 기록한다.

## 8. `pipeline_kind` 필드 추가

`stages == 2` 는 `MmaPipelined`(동기 LDG + STS), `stages >= 3` 은
`MmaMultistage`(cp.async / LDGSTS) 로 **구현이 다른 별개 커널**이다.
SASS 에서도 정확히 갈린다 (stages=2 는 LDGSTS 0 개, stages≥3 은 795/795 사용).
`stages` 를 하나의 연속 축으로 보면 잘못된 결론이 나오므로 명시적으로 남긴다.

## 9. warp tile (64,128) 제외 — 계산이 틀린다

`is_valid_kernel` 은 원칙적으로 컴파일/실행 가능성만 본다. 하지만 warp tile
`(64,128)` 은 컴파일도 되고 런치도 되는데 **결과가 틀린다.**

`scripts/check_correctness.py` 로 a888 런치 가능 커널 1,215 개를 전수 검사한
결과:

```
이상 60 / 정상 1,155
이상 커널의 warp tile: {(64,128): 60}   <- 100%, 예외 없음
같은 누산기 수(256 regs/thread)인 mirror (128,64): 60/60 정상
max_rel_error 0.77 ~ 1.13  (완전한 오답)
```

레지스터 수가 원인이 아니라 `warp_n` 이 원인이다. CUTLASS generator 가 만드는
712 개 조합 중 `warp_n >= 128` 은 1 건뿐이고 `(64,128)` 은 0 건 — 검증되지 않은
영역이다. 근본 원인은 더 추적하지 않았다.

성능 필터가 아니라 **정확성** 문제이므로 제외한다. 오답 config 가 성능표에
섞이면 그 표를 쓰는 모든 분석이 오염된다. `(128,64)` 는 정상 동작하므로
(스필로 느리긴 하지만) 남겨둔다 — 느린 것은 데이터로 남길 가치가 있다.

## 10. 측정 반복 수를 고정 하한이 아니라 시간 예산으로 정한다

원래 스펙은 "총 20ms 또는 **최소 30회**" 였다. 그 값은 노이즈가 큰 상황
(스로틀 51%, 재현성 max 8.91%)을 가정한 것이다. 클럭 고정 후에는 2,155 회
연속 측정 변동이 0.11% 라 전제가 달라졌다.

고정 하한을 쓰면 느린 커널에서 최소 반복 수가 시간을 지배한다 —
20ms 커널 × 30회 = 작업당 0.6초. 전수 측정 926,235 건에서 이것만으로
20 시간 이상이 더 든다. 그래서 규칙으로 바꿨다.

```
min_reps = clamp(ceil(min_total_ms / t), min_reps_floor, min_reps_cap)
n_reps   = clamp(target_ms / t,          min_reps,        max_reps)
     target_ms=20, min_total_ms=3, min_reps_floor=5, min_reps_cap=30
```

빠른 커널(≤0.1ms)은 예전과 같은 30회 이상, 느린 커널은 최소 3ms 만 재고
멈춘다. 하한 5 는 IQR 사분위 계산에 필요한 최소 표본이다.

**프로토콜은 `env.json` 의 `protocol` 에 기록되어 `env_hash` 에 반영된다.**
프로토콜이 바뀌면 측정 조건이 바뀐 것이므로 resume 이 예전 줄을 건너뛰면
안 되기 때문이다.

## 11. cp.async 최소 접근 폭 — alignment 1 은 2단만 가능

multistage(stages ≥ 3)는 `cp.async`(LDGSTS)로 전역→smem 복사를 하는데,
cp.async 는 **4/8/16 바이트 접근만** 지원한다. fp16 × alignment 1 = 2 바이트가
정확히 여기 걸려 `static_assert: Size is not supported` 가 난다.

실측: `a118`(K=4097) 에서 stages=2 는 31/31 성공, stages≥3 은 0/140 성공.
`is_valid_kernel` 에 넣었고 실측 2,901 건과 대조해 오탐 0 / 미탐 0 이다.

결과적으로 층 D 의 `K=4097` 형상은 유효 커널이 445 개뿐이다 (다른 alignment 는
1,305~1,435). **alignment 1 은 2단 파이프라인만 쓸 수 있다** 는 것 자체가
이 형상에 대한 결론이다.

## 12. Backend Protocol 에 메서드 추가

명세된 목록 외에 `enumerate_runtime`, `explain_kernel`, `ext_from_dict`,
`pipeline_kind`, `effective_split_k` / `workspace_bytes` 를 두었다. 각각
split-K 축 값 집합의 아키텍처 종속성, 제약 funnel 집계, JSONL 역직렬화,
파이프라인 계열 구분, CUTLASS split-K 의미론 때문이며 전부 백엔드 뒤에 있다.

## 13. 형상/조건 단위 파생 지표는 `env_hash` 별로만 계산한다

`core/table.py` 의 `load_for_ranking` 은 **소비 시점**에 `env_hash` 혼재를
막는다. 그러나 **`export.py` 에는 그 보호가 없다** — `rows` 에는 모든 측정
조건의 줄이 섞여 있고, 파생 지표를 계산하는 곳이 바로 거기다.

조건이 다르면 절대 시간이 비교 불가능하다. 그런데 형상 단위로 중앙값이나
최소값을 내는 순간 그 사실이 사라지고 **아무 오류도 나지 않은 채** 값만
틀린다.

실제로 겪었다. `difficulty = 중앙값 시간 / 최적 시간` 을 `env_hash` 없이
계산했더니 폐기된 드리프트 구간(`368a84f1`, 최대 +1380 % 오염)의 느린 시간이
섞여 **난이도가 22.05 배**까지 나왔다. 조건별로 나눈 뒤에는 1.11~2.60,
중앙 1.58 이다. 20 배 틀린 값이 예외 하나 없이 나왔다.

### 다섯 번 밟고 나서 구조로 옮겼다 (R-5)

문서에 적어 둔 다음에도 두 번 더 밟았다. 전수 조사해 보니 다섯 곳이었다.

| # | 어디 | 증상 |
|---|---|---|
| 1 | `export.py` 의 `difficulty` | 난이도 **22.05 배** |
| 2 | `bundle.py` 의 번들 통계 | 형상 68개(실제 66), 측정 구간이 폐기 구간부터. **공개 릴리즈 노트에 실릴 뻔했다** |
| 3 | `rehearse.py` 의 드리프트 경고 | 변동폭 **55.59%**, 경고 상시 발생 |
| 4 | `rehearse.py` 의 `reproducibility()` | 재현성 기준값을 **다른 조건의 측정치**에서 가져옴 |
| 5 | `recheck_stability.py` | 같은 이유로 재측정 대조가 어긋남 |

그래서 `core/records.py` 하나로 모았다.

```python
def iter_records(path, env_hash): ...       # env_hash 에 기본값이 없다
def aggregate_per_env(rows, key_fn, ...):   # 집계 키에 env_hash 가 강제로 들어간다
ALL = "ALL"                                  # 전체를 보려면 명시해야 한다
```

* `env_hash` 를 안 쓰면 `TypeError`, 빈 문자열이면 `EnvHashError` 다.
  **우회로를 남기지 않는다.**
* 집계는 키에 `env_hash` 가 강제로 들어가므로 섞는 것이 불가능하다.
* `tests/test_records.py` 가 이것을 고정하고, **실제 호출부가 필터를
  쓰는지도** 검사한다 (새로 추가한 사람이 빠뜨리면 거기서 걸린다).

예외는 `validate_table.py` 하나다 — "파일에 조건이 몇 종 섞여 있는가" 를
보고하는 것이 그 검사기의 일이라 의도적으로 전체를 읽는다. 주석에 명시했다.

### 여섯 번째는 성격이 달랐다 — **배포 경계**

앞의 다섯은 전부 **코드 안에서 집계가 오염**된 것이라 `core/records.py` 로
막을 수 있었다. 여섯 번째는 아니었다.

`bundle.py` 가 `results/table.parquet` 을 **파일째 복사**해서, 폐기한 드리프트
데이터 226,145행이 공개 GitHub Release 에 실렸다. 원본은 작업 파일이라 여러
조건을 담는 것이 정상이고(조건 간 비교/드리프트 분석에 쓴다), 문제는 그것이
**걸러지지 않고 경계를 넘어간 것**이다.

`BUNDLE.json` 의 `n_rows` 는 필터한 값이라 980,915 로 **맞았다.** 그래서
아무도 못 알아챘다 — 통계는 맞는데 파일이 틀렸다.

```
읽기 층   iter_records(path, env_hash)     <- 집계 오염을 막는다
배포 층   validate_bundle(dir)             <- 파일이 경계를 넘는 것을 막는다
```

배포 층 검사의 핵심은 **`n_rows` 와 실제 행 수의 일치**다. 그 불일치가
"통계만 필터하고 파일은 안 걸렀다" 의 서명이고, 이 검사 하나면 바로 잡혔다.
`bundle.py` 는 이 검사를 통과하지 못하면 번들을 만들지 않는다.

교훈: **강제 지점은 데이터가 층을 넘는 곳마다 필요하다.** 읽기를 막았다고
쓰기·복사·배포가 안전해지지 않는다.

### 일곱 번째는 **같은 층의 다른 경로**였다 (R-4)

여섯 번째까지는 층이 달랐다. 일곱 번째는 층도 같고 파일도 같은데 **경로가
둘**이었다.

P-2 에서 GPU 선택 경로를 UUID 기준으로 바꾸고, UUID 를 못 찾으면 인덱스로
폴백하던 것을 `DeviceNotFoundError` 로 바꿨다. 그런데 `measure/gpu_state.py`
의 `NvmlProbe.__init__` 에 **NVML 핸들을 얻는 폴백이 따로 남아** 있었다.

```python
try:
    self.h = nvml.nvmlDeviceGetHandleByUUID(uuid.encode())
except Exception:
    self.h = nvml.nvmlDeviceGetHandleByIndex(index)   # <- 다른 GPU
```

결과는 **측정은 GPU 3 에서 하는데 클럭·온도는 다른 GPU 것을 기록**하는
것이다. 그리고 그 값으로 "33 시간 동안 조건이 유지됐다" 를 판정한다.
측정값 자체는 맞는데 **그것을 믿을 근거가 조용히 가짜가 된다.**

| | 6번째 | 7번째 |
|---|---|---|
| 무엇이 달랐나 | 층이 달랐다 (읽기 vs 배포) | **같은 층, 다른 경로** |
| 왜 놓쳤나 | 배포 층에 검사가 없었다 | 한 경로를 고치고 끝냈다 |
| 무엇으로 막나 | `validate_bundle()` | `tests/test_device.py` + `test_gpu_state.py` 가 **두 경로 모두** UUID 실패 시 예외를 요구 |

교훈을 한 줄 더 붙인다: **같은 클래스의 버그를 한 곳에서 고쳤으면, 그
클래스를 전수 검색하라.** "GPU 를 인덱스로 여는 곳" 을 `grep` 한 번 했으면
같은 커밋에서 잡혔을 것이다. 실제로 이 프로젝트에서 전수 검사가 통했던
사례가 이미 있었다 — `MEM_CLOCK_MIN_FRAC` 미구현을 AST 검사로 찾았다.

### 순위 변화를 성능 변화로 읽지 마라

두 캠페인 표를 대조했더니 이렇게 나왔다.

    최적 config 가 그대로인 형상        15/66 (23 %)
    옛 최적이 새 표에서 노이즈 이내      50/66 (76 %)

**두 줄이 함께 있어야 진실이 보인다.** 앞 줄만 보면 "순위가 77 % 뒤집혔다
= 표에 유통기한이 있다" 로 간다. 뒷줄이 그것을 반박한다 — 옛 최적은
대부분 **여전히 새 최적과 구분되지 않는다.**

원인 특정도 지표가 있어야 됐다.

| 상위 20 Jaccard 와의 상관 | r |
|---|---|
| `distinct_time_frac` (계측 분해능) | **+0.582** |
| `log(최적 시간)` | +0.699 |
| 난이도 (물리) | +0.184 |

**churn 은 분해능 현상이지 성능 변화가 아니다.** 실제로 형상별 최적 시간은
중앙 +0.00 % 로 안 변했다. 성능이 그대로인데 순위가 절반 바뀐 것이다.

`distinct_time_frac` 을 넣어 두지 않았으면 "순위가 절반 바뀌었다" 로만 보고
**틀린 결론**에 갔을 것이다.

규칙: **순위가 바뀌었다는 관찰만으로 결론 내지 마라.** 계측 분해능 안에서
자리를 바꾸는 것과 실제로 뒤집히는 것은 다르고, **두 지표를 함께 봐야**
구분된다.

> 같은 교훈이 축 판정에도 적용됐다. "최적 0 회" 로 제외 후보를 정했는데
> **정답 집합 기준으로 다시 재니 6 개 중 3 개가 뒤집혔다** — `stages=8` 은
> 한 번도 1 등이 아니면서 10 형상에서 1 등과 구분 불가능했다.
> 빼면 그 형상들에서 동점 최적을 잃는다.

### 열 번째 — **같은 판정이 여덟 곳에** (무엇이 측정인가)

`results.jsonl` 에는 측정 줄과 cuBLAS 참조 줄이 섞여 있다. 그 구분을
**여덟 곳이 각자** 하고 있었다.

    rehearse / export / validate_table / report_phase3 / report_rehearsal
    recheck_stability / sweep_status / (그리고 소비 쪽이 밟을 자리)

전부 `kernel_id == "cublas"` 라는 **문자열 비교**였다. 그리고 그중 하나
(`sweep_status.py`)가 참조 줄을 측정과 함께 세서 진행률이 **101.2 %** 로
나왔다.

> 지적은 "소비하는 쪽이 밟을 수 있다" 였는데, **이미 저장소 안에 여덟 개
> 경로가 흩어져 있었다.**

`core.records.is_reference()` 하나로 모았다. 그리고 새로 기록되는 줄에는
`record_kind: "reference"` 를 넣되, **옛 줄은 `kernel_id` 로 떨어지게**
했다 — 두 경로를 그 함수 하나만 안다.

규칙: **같은 판정을 여러 곳에서 하면 그중 하나는 반드시 어긋난다.**
"조건 판정" 을 발견하면 그 자리를 고치지 말고 **판정 함수 하나로 모으고,
문자열 직접 비교를 테스트가 잡게** 하라. `env_hash` 격리(13 번)와 같은
뿌리다 — 이번엔 "무엇이 측정인가" 였다.

### 아홉 번째 — **패키지 안팎을 헷갈린 경로** 세 건

패키지 이전(`core/` → `kerneltab/core/`) 뒤 "이 디렉토리가 패키지 안인가
밖인가" 를 틀린 곳이 셋 나왔다. 전부 같은 클래스인데 **드러난 시점이 전부
달랐다.**

| 무엇 | 어떻게 드러났나 |
|---|---|
| `hwspec/` | 이전 중에 잡았다 (의식하고 있었다) |
| `build/launch_probe.cu` | **컨테이너에서 `detect` 가 죽었다** |
| `datasets/` | **릴리즈 번들을 실제로 열어 보고서야** |

셋째가 가장 아슬아슬했다. 호스트에서 312 개 테스트가 통과하고 있었고,
`datasets/` 는 코드가 평소에 안 건드리는 경로라 아무 데서도 안 보였다.
**소비 프로젝트(kernelRule)가 첫 번째로 밟았을 버그다.**

세 가지로 대응했다.

1. **구분을 한 곳에 적었다.** `paths.PACKAGE_INTERNAL` / `PACKAGE_EXTERNAL`
   과 그 이유를 `core/paths.py` 상단 표에.
2. **검사로 강제했다.** `tests/test_paths.py::TestPackageBoundary` 가
   `PKG_ROOT / "<패키지 밖 이름>"` 과 그 반대를 AST/정규식으로 잡고,
   경로 결정이 `paths.py` 밖에 있으면 실패한다.
3. **결정 지점을 하나로 모았다.** `datasets/` 루트를 `core/bundle.py` 와
   `scripts/bundle.py` 가 **각자** 정하고 있었다 — 그래서 한쪽만 어긋났다.

그리고 `paths.py` 를 `build/` 에서 `core/` 로 옮겼다. 이름이 "빌드 경로" 인데
`RESULTS_DIR` / `HWSPEC_DIR` / `datasets_dirs()` 를 들고 있었다.
**"datasets 루트를 어디서 정하나" 를 찾는 사람이 `build/` 를 뒤지지 않는다** —
이 사고의 뿌리가 기능이 아니라 **발견 가능성**이었기 때문에 이름을 고쳤다.
덤으로 `core → build` 레이어링 역전도 사라졌다.

> ⚠️ 실행 비용은 없었다. `build/__init__.py` 가 비어 있어서 무거운 것이
> 딸려오지도 않았다. **비용이 없다고 안 고치면 안 되는 종류가 있다** —
> 사람이 못 찾는 구조가 그것이다.

### 여덟 번째 — 술어 하나가 **일곱 곳**에 복사돼 있었다

`launchable` (= `regs_per_thread * threads <= regs_per_sm`) 판정이 일곱 곳에
따로 있었다. 식은 같은데 **결측 처리가 서로 달랐다.**

| 어디 | 결측일 때 |
|---|---|
| `rehearse.py::launchable()` | `True` |
| `export.py` 의 `launchable` 컬럼 | `None` |
| `validate_table.py` / `check_correctness.py` / `recheck_stability.py` / `verify_clock_lock.py` / `smoke_splitk.py` | 인라인, 통과시킴 |

`core/kernels.py` 하나로 모았다. 그런데 **여기서 방법론이 갈렸다.**

`grep` 으로 찾은 것은 여섯 곳이었다. 일곱 번째(`smoke_splitk.py`)는
**테스트가 찾았다** — `tests/test_kernels.py` 가 AST 를 훑어
`regs_per_thread` 와 `threads` 를 곱하는 곳이 있으면 실패한다. 표현이 조금
달라(`r["regs_per_thread"]` vs `r.get("regs_per_thread")`) grep 패턴을
빠져나갔던 것이다.

교훈: **"전수 검색했다" 를 사람의 grep 으로 끝내지 마라.** 같은 검색을
테스트로 만들면 지금 찾을 뿐 아니라 **다음에 추가되는 것도 막는다.**
`docs/decisions.md` 15 의 "코드로 강제할 방법이 있는가" 와 같은 이야기이고,
이번에는 그 질문이 실제로 한 건을 더 잡았다.

교훈은 더 넓다 — **`env_hash` 는 조인 키가 아니라 격리 경계다.** 두 조건의
줄이 같은 집계에 들어가는 경로가 생기면, 그 지표는 조용히 틀린다.

### 컨테이너가 여섯 개를 더 찾았다 (2026-08-20)

호스트에서 268 개 테스트가 전부 통과하는 상태에서 이미지를 만들었더니
**여섯 개가 더 나왔다.** 전부 "호스트에서는 안 밟는" 것이었다.

| # | 무엇 | 왜 호스트에서는 안 보였나 |
|---|---|---|
| 1 | `VOLUME` 이 바인드 마운트를 덮는다 | 컨테이너에만 있는 개념 |
| 2 | `cutlass.commit` 이 `null` 인 `env.json` | git 의 "dubious ownership" 은 **`--user` 로 돌릴 때만** 난다 |
| 3 | `tomllib` 은 3.11 stdlib | 개발 Python 은 3.13 |
| 4 | `launch_probe.cu` 경로가 이전 후 그대로 | 호스트에서 `phase0_env.py` 를 다시 돌린 적이 없었다 |

| 6 | `manifest tree_hash` 가 반쪽만 해싱 | 오류가 안 나므로 어디서도 안 보인다 |

2 번이 가장 위험했다. `cutlass.commit` 은 `env_hash_v2` 의 키다. `null` 이면
**CUTLASS 버전을 바꿔도 같은 `env_hash`** 가 나온다 — `env_hash` 를 격리
경계로 쓰는 이 저장소의 모든 보호가 그 순간 무의미해진다. 그리고 아무
오류도 나지 않는다.

교훈 둘.

* **"테스트가 전부 통과한다" 는 "그 환경에서 통과한다" 는 뜻이다.**
  이식성은 실행해 봐야 안다. vermin 같은 정적 검사는 3 번을 잡았지만
  `tests/` 를 대상에 넣고 돌린 적이 없었고, 나머지 다섯은 애초에 정적으로
  잡을 수 없는 종류다.
* **`--user` 로 돌려라.** root 로 돌리면 2 번과 1 번이 둘 다 숨는다.
  편한 쪽으로 돌리면 프로덕션에서만 터진다.

그리고 5 번은 이전 탓이 아니라 **원래 깨져 있었다.** 언제부터인지 추적했다.

| 검사 | 범위 | 결과 |
|---|---|---|
| `build_kernels.py` (빌드마다) | 빌드된 커널 **전부** | `smem_computed` vs `smem_dynamic` 불일치 0 |
| `validate_constraints.py` | 캠페인 **7,330 개 전부** | 불일치 **0/7,330** |
| ~~`check_smem.py`~~ | 표본 40 개 | 깨져 있었음 |

둘 다 `cudaFuncGetAttributes` 의 실측 smem 을 기준으로 쓴다 —
`check_smem.py` 가 쓰려던 `sizeof(SharedStorage)` 와 같은 진실이고 범위는
183 배 넓다. **`check_smem.py` 는 중복이었고, 그 침묵은 아무 대가도 없었다.**

교훈은 그래도 남는다: **중복 검사라도 깨진 채로 두면 안 된다.** "돌렸는데
통과했다" 와 "돌렸는데 아무것도 검사 못 했다" 가 구분되지 않으면, 다음에
진짜로 유일한 검사가 같은 방식으로 죽어도 똑같이 안 보인다.

절차를 문서에 적어 두는 것만으로는 부족하다 — **이미지 빌드가 테스트를
돌리게** 만들어 두었다.

> 곁가지로 하나 더 나왔다. `validate_constraints.py` 가
> "저장된 `smem_computed` 가 현재 공식과 다른 줄: **120**" 을 보고한다.
> 공식을 한 번 고쳤고 `kernels.jsonl` 은 append-only 라 옛 값이 남아
> 있는 것이다. `export.py` 는 항상 재계산하므로 표는 맞다.

### 그리고 더 나쁜 변형 — **조용히 잘못된 값으로 진행**

14 번은 "조건이 안 맞으면 조용히 통과" 다. `cutlass.commit` 이 `null` 인
`env.json` 은 그것의 **한 단계 나쁜 변형**이었다.

| | 14 번 (조용한 통과) | 이번 (조용한 오답) |
|---|---|---|
| 무엇이 일어나나 | 검사가 아무것도 안 한다 | **해시가 계산된다** |
| 결과물 | 없음 | **그럴듯한 값** |
| 사후에 알 수 있나 | "검사 결과가 없네" 로 눈치챌 여지 | **없다.** 값이 있으니 정상으로 보인다 |
| 무엇이 망가지나 | 그 검사 하나 | **격리 경계 전체** |

`env_hash` 는 조인 키가 아니라 **격리 경계**다 (13 번). 필수 입력이 `null`
이면 서로 다른 CUTLASS 버전이 같은 해시를 받고, 그 뒤로는 이 저장소의 모든
`env_hash` 기반 보호 — `iter_records`, `aggregate_per_env`,
`validate_bundle` — 가 **정확히 동작하면서 틀린 답**을 준다.

그래서 `env_hash_v2()` 는 필수 키가 비면 계산하지 않고 `EnvHashIncomplete`
를 던진다. 값을 안 주는 것이 틀린 값을 주는 것보다 낫다.

규칙: **"기본값을 넣어 계속 진행" 을 쓰기 전에, 그 기본값이 틀렸을 때
누가 알아채는지 물어라.** 아무도 못 알아챈다면 예외가 맞다.

### `env_hash` 는 **조건**의 경계이지 **실행**의 경계가 아니다

13 번은 지금까지 "섞이면 안 되는 것" 만 다뤘다. 이번 것은 반대다 —
**섞여야 하는데 세는 단위가 다른 경우.**

전수 시작 30 분 시점 보고를 내려다 숫자가 틀린 것을 잡았다.

    측정 150,868 / 980,915 (15.4%)   86.3/s   ETA 2.7h
    라운드 [0,1,2,3]  슬라이스 63
    ** sweep_done: 라운드 4, 2.5h **

**86.3/s 는 물리적으로 불가능하다.** 실측이 14~17/s 인 것을 알고 있었기에
튀는 것을 알아챘다. 원인은 G-7(검증)과 G-8(전수)이 **같은 `env_hash`** 를
쓰기 때문이다 — 같은 조건이어야 재개가 되므로 그것이 설계다. 그런데
진행률과 속도를 통째로 합치면 분자에 G-7 의 120,000 줄이 들어가고 분모는
G-8 의 0.5 시간이라 속도가 6 배로 부푼다. 라운드·슬라이스·`sweep_done` 도
전부 G-7 것이었다.

| | 무엇을 세는가 | 경계 |
|---|---|---|
| 캠페인 완료율 | 이 조건에서 측정된 **모든** 줄 | `env_hash` (G-7 줄도 진짜 데이터다) |
| 속도 / ETA | **이번 실행**에서 측정된 줄 | `sweep_start` 이후 |
| 라운드 / 슬라이스 | 이번 실행 | `sweep_start` 이후 |

규칙: **`env_hash` 로 걸렀다고 집계 단위가 정해지는 것이 아니다.** "무엇의
비율인가" 를 먼저 정하고 분자와 분모의 경계를 맞춰라. 이것은 sB/sW,
워밍업 대조군, 앵커 라운드 매핑에서 반복된 것과 같은 원칙이다.

### 보정은 **없던 신호를 만들어낼 수 있다**

워밍업 시간 예산화가 측정값을 바꾸지 않는지 검증하면서 판정 기준을 **두 번**
틀렸다. 두 번 다 "실패" 가 나왔고, 두 번 다 **변경 탓이 아니었다.**

**1차 — 노이즈 모델만으로 판정.** `core/noise.py` 의 `sigma_rel(t)` 대비로
쟀더니 프로토콜이 **완전히 같은** 조합이 +0.30 % 로 실패했다
(`warm 10->10`, 오버헤드 `100.2 -> 100.2 ms` — 두 실행이 한 일이 같다).
모델은 앵커 커널에서 뽑은 것이고 커널마다 실제 산포가 다르다.

**2차 — 선형 추세 보정.** `옛A / 새 / 옛B` 로 재고 `rel - rel_ctrl/2` 로
창 안의 추세를 뺐다. 그랬더니 **세 조합이 실패로 찍혔는데 셋 다
`새-옛 = +0.00%`** 였다. 원래 차이가 정확히 0인데 보정이 만들어낸 것이다.

원인은 양자화다. 짧은 커널의 중앙값은 CUDA 이벤트 타이머 눈금(1.024 us)에
붙어 있어서, 대조군이 **한 눈금** 움직이면 그 절반이 보정으로 들어간다.
매끄러운 추세를 가정할 수 없는 데이터에 추세 보정을 쓴 것이 잘못이다.

**최종 기준:**

> **같은 프로토콜로 두 번 재서 X 만큼 달랐다면, 프로토콜 간 X 이하의
> 차이는 증거가 아니다.**

    새 - 옛  <=  max(k x SE, 노이즈 바닥, |옛A - 옛B|)

대조군을 **허용치에** 넣는다. 빼지 않는다. 그리고 **방향도 본다** —
워밍업이 부족하면 새 쪽이 느려져야 한다. 빨라지는 이탈은 그 가설로
설명되지 않으므로 주의로만 찍는다.

교훈 둘.

* **대조군은 모델이 아니라 같은 조건의 반복 측정이어야 한다.** 모델은
  다른 데이터에서 뽑은 요약이고, 이 조합에서 맞는다는 보장이 없다.
  이것은 앵커 판정에서 `sW` 를 "같은 슬라이스의 start/end 쌍" 으로 잡은
  것과 같은 원칙이다 (R-6).
* **보정은 신호를 만들어낼 수 있다.** 빼기 전에 "그 보정이 성립하려면
  데이터가 어떤 모양이어야 하는가" 를 물어라. 양자화된 중앙값에 선형
  추세를 가정하면 안 된다.

> 이 기준은 **kernelRule 의 채점 설계에도 그대로 적용된다.** 규칙 A 와 B 의
> regret 차이를 판정할 때, 분모는 "같은 규칙을 두 번 평가했을 때의 차이"
> 여야 한다 — 노이즈 모델이 아니다.

## 13-b. `can_implement()` 를 유효성 신탁으로 쓰지 마라 — `stages=1`

축 덮개 점검(`scripts/check_axis_coverage.py`)에서 나왔다. 벤더 휴리스틱이
`stages=1` 을 15회 추천하기에 "우리가 안 재는 값인가" 를 확인했다.

sm_86, `tb=128x128x32 / warp=64x64x32`, fp16 in / fp32 accum, M=N=256 K=128:

| stages | nvcc | `can_implement()` | 실행 | 참조와 일치 | SASS |
|---|---|---|---|---|---|
| **1** | OK | **kSuccess** | OK | **65,536 중 62,674 불일치** (최대 상대오차 32) | LDGSTS 8 |
| 2 | OK | kSuccess | OK | 정확히 일치 | LDGSTS 0 (`MmaPipelined`) |
| 3 | OK | kSuccess | OK | 정확히 일치 | LDGSTS 24 |

`stages=1` 은 조용히 2단으로 떨어진 것이 아니다 — LDGSTS 가 있으므로 실제로
1단 멀티스테이지 경로를 타고, **그 경로가 틀린다.**

### 무서운 부분

우리 열거기의 `explain_kernel()` 도 `stages=1` 을 `valid` 로 판정한다.
컴파일도 되고, CUTLASS 자신도 통과시키고, 실행도 성공한다. **`STAGES` 축
목록에 1 이 없다는 것이 유일한 방어였다.**

```
유효성 검사     통과시킨다
can_implement   통과시킨다
컴파일          통과한다
실행            성공한다
축 목록         ← 여기서만 막혔다
```

### 규칙

**축 목록은 "탐색 범위" 가 아니라 안전장치이기도 하다.** 축에 값을 더할
때는 `can_implement()` 나 컴파일 성공을 근거로 삼지 말고 **참조값과 원소
비교까지** 한다. `check_axis_coverage.py` 의 `KNOWN` 에 그 절차를 못박아
뒀다.

이것은 14번("조용히 통과하는 안전장치를 금지한다")의 외부 판본이다 —
우리 코드가 아니라 **라이브러리가** 조용히 통과시켰다.

## 14. 조건이 안 맞으면 조용히 통과하는 안전장치를 금지한다

이 저장소가 **같은 클래스의 버그를 네 번** 만났다.

| # | 사례 | 증상 |
|---|---|---|
| 1 | `WARMUP_SECONDS` | 정의만 되고 안 쓰임. **로그는 "워밍업 한다" 고 찍혔다** |
| 2 | `MEM_CLOCK_MIN_FRAC` | 주석에 판정 기준만 있고 미구현 |
| 3 | `test_table.py` / `test_bundle.py` | pyarrow 가 없으면 41개가 통째로 스킵되는데 **"86 passed" 초록불** |
| 4 | `drift_check()` | 프로브 커널 준비가 실패하면 `return` (None). 호출부는 `if t_drift:` 라 **드리프트 감시가 조용히 멈춘다** |

공통점은 하나다 — **실패했다는 사실이 아무 데도 남지 않는다.** 결과만 보면
정상과 구분이 안 된다. 1번은 33시간 측정에 냉시작 104회를 섞을 뻔했고,
3번은 정답 누출 방지가 검증됐다고 거짓으로 믿게 했다.

### 규칙

**"할 수 없으면 아무것도 안 한다" 는 금지한다.** 셋 중 하나를 골라야 한다.

1. **실패시킨다** — 검증/테스트 경로의 기본값. 조용한 통과보다 시끄러운
   실패가 낫다.
2. **크게 남긴다** — 측정 루프처럼 멈추면 더 곤란한 경우. 경고를 찍고
   **기록에 플래그를 남겨** 사후에 걸러낼 수 있게 한다
   (`soak_info.warmup_mem_clock_ok` 가 그 예다).
3. **명시적으로 우회시킨다** — 환경변수 등으로 의도를 드러내게 하고,
   우회했다는 사실이 출력에 남게 한다 (`KERNELTAB_ALLOW_SKIP=1`).

### 강제 방법

문서로 적어두는 것으로는 부족하다 — 1번을 고치고 나서 2번을, 그 다음
3번을 밟았다. **구조로 막는다.**

* `tests/conftest.py` 가 중요 모듈이 실제로 돌았는지 **합성 테스트 항목**으로
  검사한다. `pytest_sessionfinish` 에서 `session.exitstatus` 를 바꾸는 방법은
  pytest 버전에 따라 전파되지 않는다(실제로 메시지만 나오고 exit 0 이었다).
  진짜 테스트 항목이어야 종료 코드로 이어진다.
* `tests/test_skip_guard.py` 가 **그 감시가 실제로 실패를 잡는지** 확인한다.
  감시에 감시가 없으면 감시 자체가 이 병에 걸린다.
* AST 전수 검사로 남은 사례를 찾는다 (`except: pass`, 검증 함수의 조용한
  `return`). 현재 17건 + 1건이 남아 있고 `docs/pending_fixes.md` R-4(b) 에서
  하나씩 판정한다.

## 15. 메타 — 문서로 적은 규율은 지켜지지 않는다

이 저장소에서 가장 여러 번 확인된 사실이다.

| 규율 | 어디에 적었나 | 그 뒤 몇 번 더 밟았나 |
|---|---|---|
| "조건이 안 맞으면 조용히 통과하지 마라" | 코드 주석 | **3번** (`MEM_CLOCK_MIN_FRAC`, `test_table.py`, `drift_check`) |
| "`env_hash` 는 격리 경계다" | `decisions.md` 13번 | **2번** (`bundle.py` 통계, `reproducibility()`) |
| "`status != ok` 는 결측이 아니다" | `consumer_contract.md` §9 | **4곳** (`baseline_*`, `export`, `compare_campaigns`, `report_phase3`) |

두 경우 모두 **교훈을 명시적으로 적어 둔 다음에** 같은 실수를 반복했다.
적는 것이 무용하다는 뜻이 아니라, **적는 것만으로는 부족하다**는 뜻이다.
사람이든 모델이든 코드를 쓸 때 문서를 다시 읽지 않는다.

### 규칙 — 계약 문서에는 **그 계약을 검사하는 테스트**를 붙인다

**계약 문서가 옳아도 코드가 반대면 아무도 못 본다.**

`consumer_contract.md` §9 는 "`status != ok` 는 결측이 아니다" 라고 옳게
적혀 있었는데, `baseline_*.py` 는 정확히 반대로 하고 있었다. 앞의 두
사례(13번, 14번)보다 한 층 더 나쁘다 — **문서를 믿었으니 아무도 코드를
안 봤다.** 그 결과 정적 top-1 이 1.115 인데 1.394 로 공개 문서에 실렸고,
"전 형상에서 측정된 config" 가 3,465 개가 아니라 3 개였다.

```
consumer_contract §9  "status != ok 는 결측이 아니다"
코드                   반대로 하고 있었다
있었어야 할 것         "ok 만으로 집계하는 곳이 없다" 를 AST 로 검사하는 테스트
```

지금은 `tests/test_contracts.py` 가 그것을 한다. 검사를 **파일 단위 허용
목록**이 아니라 **줄 단위 표시(`# status-filter: <이유>`)** 로 만든 것이
요점이다 — `export.py` 는 정당한 비교(정책 게이트)와 틀린 비교를 **같은
파일 안에** 갖고 있었다. 파일을 통째로 면제했으면 못 잡는다.

같은 방식을 C-1 에도 썼다. `core/noise.py` 의 모듈 전역
(`noise_floor`, `sigma_rel`, `tick_pct`, `resolvable`)을 지운 뒤,
**그 이름이 되살아나는지**와 **누가 import 하는지**를 테스트가 훑는다.
지우기만 하면 다음 사람이 "편의 함수" 로 다시 만든다.

**규율을 정할 때마다 "이것을 코드로 강제할 방법이 있는가" 를 먼저 묻는다.**
없으면 그 규율은 지켜지지 않을 것이라고 전제하고, 다음 중 하나를 찾는다.

| 강제 수단 | 이 저장소의 예 |
|---|---|
| 타입/시그니처로 불가능하게 | `iter_records(path, env_hash)` — 기본값이 없어 안 쓰면 `TypeError` |
| 키에 강제로 포함 | `aggregate_per_env()` — 집계 키에 `env_hash` 가 들어가 섞을 수 없다 |
| 테스트가 **호출부까지** 검사 | `test_records.py::TestCallersFilter` — 새로 추가한 사람이 빠뜨리면 걸린다 |
| 감시에 감시를 붙임 | `test_skip_guard.py` — 스킵 감시가 실제로 실패를 잡는지 확인 |
| 기본값을 안전한 쪽으로 | `answer_set(tol=None)` -> 형상별 노이즈 바닥 |
| **기본값이 없으면** 명시하게 | `answer_set(noise=...)` 필수 -> 안 주면 `NoiseCoefRequired` |
| 지운 이름이 되살아나는지 검사 | `test_contracts.py` — `noise_floor` 등 모듈 전역 |
| 거를 때마다 이유를 적게 | `# status-filter:` 표시 + AST 검사 |

`answer_set` 이 이 원칙의 좋은 예다. 고정 `tol=0.01` 을 기본값으로 두면
**아무도 안 바꾼다** — 편해서가 아니라, 바꿔야 한다는 사실을 모르기
때문이다. `tol=None` 이 기본이고 형상별 노이즈 바닥을 쓰면, 고정값을
쓰려는 사람이 **명시적으로 근거를 대야** 한다. 그리고 "15 us 에서 1 % 는
구분 불가" 를 테스트(`test_noise.py`)로 고정해 두면 편의상 되돌리는 것도
막힌다.

헬퍼만 만들고 "이걸 쓰세요" 를 문서에 적는 것은 **강제가 아니다.**
`core/records.py` 를 만들 때 호출부 검사 테스트를 같이 넣지 않았다면
여섯 번째를 밟았을 것이다.

### 남는 한계

전부를 코드로 강제할 수는 없다. 강제할 수 없는 규율은 **적어도 그 사실을
명시**하고(`docs/next_campaign.md` 의 "새 GPU 에서 다시 재야 하는 값"),
체크리스트로 만들어 실행 시점에 읽히게 한다 — 설계 시점에 읽는 문서보다
낫다.

## 16. 클럭 고정이 실효 피크를 반드시 낮추는 것은 아니다 (RTX 5090)

A6000 에서 굳어진 직관이 5090 에서 뒤집혔다. 문서 곳곳이 "클럭을 고정하면
스펙 피크를 그대로 쓸 수 없다 — ridge point 가 실제보다 **높게** 나온다" 로
적혀 있는데, 그 방향은 하드웨어에 달려 있다.

| | A6000 | **RTX 5090** |
|---|---|---|
| 정격 부스트 | 1800 MHz | 2407 MHz |
| 고정값 | 1350 MHz | **2692 MHz** |
| 실효 피크 | 154.8 -> **116.1** (낮아짐) | 209.5 -> **234.3** (★ 높아짐) |
| 미고정 시 상태 | `sw_power_cap` 51 % — **전력에 굶주림** | 스로틀 0 %, 전력 여유 127 W |

A6000 은 전력에 굶주려서 관찰 범위(1485~1935)보다 한참 아래로 내려야 했다.
5090 은 정격 부스트보다 **20 % 위**에서 스로틀 없이 돌기 때문에, 관찰된
정상 상태 하한(2880)보다 조금 낮게 잡으면 그 값이 정격 부스트보다 높다.

`phase0_env.py` 의 비례식(`peak * locked_mhz / peak_tflops_f16_at_mhz`)은
양방향 모두 맞게 동작한다. **틀리는 것은 코드가 아니라 직관이다.**

### 그리고 고정이 전력을 낮췄다

```
미고정  469 W   (SM 2880 MHz)
고정    389 W   (SM 2692 MHz)
클럭은 6.5 % 내렸는데 전력은 17 % 내려갔다 — 전압-주파수 곡선이 비선형이다
```

**"고정 = 성능 하향" 이 아니라 "고정 = 변동 제거" 다.** 그리고 5090 에서는
열 여유까지 덤으로 생긴다 (68 -> 65 C).

### 요청값과 실측값이 다르다

`nvidia-smi -lgc 2700,2700` 을 걸었는데 실제로는 **2692 MHz** 가 됐다. SM
클럭은 7~8 MHz 간격의 이산값이고 드라이버가 지원 목록의 값으로 스냅한다.

**파생값은 전부 실측값 기준으로 계산해야 한다.** 2700 으로 계산하면 실효
피크가 235.0, 2692 로 계산하면 234.3 이다. `phase0_env.py` 에 넘기는
`--externally-locked-mhz` 는 **요청값이 아니라 20 분 관찰의 실측값**이다.

## 17. 백엔드 이름은 아키텍처가 아니라 **API 계열**로 짓는다

`backends/sm80.py` / `Sm80Backend` / `Sm80Ext` -> `backends/cutlass_v2.py` /
`CutlassV2Backend` / `CutlassV2Ext`.

이름이 실제와 어긋나 있었다. 이 파일이 정하는 것은 **CUTLASS 2.x API 계열**
이지 타겟 SM 이 아니다. `ArchTag` 로 쓰는 `cutlass::arch::Sm80` 은 "이 기능을
지원하는 최소 SM" 을 뜻할 뿐이고, **실제 타겟 SM 은 `nvcc -arch` 가 정한다.**
파일 docstring 이 이미 그렇게 말하고 있었는데 파일 이름만 따라가지 않았다.

sm_120(Blackwell)을 넣으면서 그것이 드러났다 — 옛 이름이었다면 "Blackwell 을
SM80 백엔드가 처리한다" 가 된다. 같은 2.x 커널이 sm_86 과 sm_120 에서 빌드도
되고 **참조 GEMM 과 수치까지 일치**한다 (12/12, split-K serial/parallel 포함).

같은 이유로 `sm90.py` 계획도 `cutlass_v3.py` 로 바꿨다. 3.x 는 SM90 "전용" 이
아니라 "이상용" 이다.

### 캠페인 **사이**가 리네임의 유일하게 안전한 시점이다

측정 중에는 `env_hash` 판정이 흐려지고(코드 수정이 해시에 안 잡힌다),
캠페인이 쌓이면 옛 이름으로 만들어진 번들이 늘어난다. A6000 은 끝났고
5090 은 한 줄도 안 쟀으므로 지금이 그 창이다.

**`env_hash` 가 안 바뀌는 것을 실증으로 확인하고 진행했다.** `ENV_HASH_KEYS_V2`
어디에도 백엔드 클래스 이름이 들어가는 경로가 없고(`manifest_hash` 는 명시적
제외), A6000 조건을 흉내낸 env 로 계산한 `env_hash_v2` 가 리네임 전후로
동일했다. 직렬화도 안전하다 — `kernels.jsonl` 은 `asdict(cfg.ext)` 로 **필드만**
싣고 `ext_from_dict()` 로 되읽으므로 클래스 이름 문자열이 파일에 없다.
**A6000 번들은 재생성하지 않아도 된다.**

## 18. 어떤 값이 다른 환경 상수의 정수배로 보이는 것은 **양자화의 증거가 아니다**

> ### 이력
>
> | 날짜 | 무엇 |
> |---|---|
> | 2026-08-29 | "다른 GPU 눈금의 정수배로 보이는 것은 양자화의 증거가 아니다. **격자를 직접 확인하라.**" 그렇게 확인해 눈금을 **32 ns** 로 결론냈다 |
> | 2026-08-31 | ⛔ **그 확인 방법에도 함정이 있었다.** 진짜 눈금은 **16 ns** 다. 절대값이 아니라 **간격**을 보고, 정수로 스냅한 뒤 검증하고, 설명력이 같으면 가장 거친 후보를 골라야 한다 — `decisions.md` 26 |
>
> 아래 본문의 교훈("격자를 직접 확인하라")은 그대로 옳다. **빠진 것은
> 그 확인을 어떻게 하느냐였다.** 이 프로젝트에서 반복되는 형태다 —
> 검사기·계측·확인 방법 자체가 결함을 만든다.


5090 에서 `launch_probe` 의 브래킷 값이 A/B 두 실행에서 정확히 같은
`0.004096 ms` 로 나왔다. A6000 의 `EVENT_TICK_MS = 0.001024` 의 **정확히 4 배**
였고, 두 번 재서 같은 값이 나왔다는 것이 양자화를 강하게 시사했다. 가설을
둘로 좁혔다 — (a) 눈금 1.024 us 에 브래킷이 4 눈금, (b) 눈금이 4.096 us.

**둘 다 틀렸다.** 짧은 커널을 개별 event bracket 으로 10,000 회 재고 서로 다른
값의 최소 간격을 보니 **32 ns** 였다 (A6000 의 1/32). 고유값 92 개가 32 ns
격자 위에 정확히 놓인다 — `0.001984`(62 눈금) `0.002016`(63) `0.002048`(64) ...

`4.096 us` 는 양자화 인공물이 아니라 **실제로 잰 브래킷 오버헤드**였다.
마침 128 눈금이라 둥글게 보였을 뿐이다.

### 규칙

**격자를 직접 확인하라.** "이 값이 저 상수의 정수배다" 는 우연히 성립하기
쉽다 — 특히 두 상수가 모두 2 의 거듭제곱일 때. 양자화를 주장하려면
**고유값들이 그 간격 위에 놓이는지**를 봐야 하고, 그것은 표본이 있어야
알 수 있다. 중앙값 하나로는 절대 판정할 수 없다.

`core/noise.py` 의 `tick_ms_observed()` 가 그 검사다. 새 환경에서는 상수를
옮기지 말고 **이 함수를 돌려라.**

> 다행히 결과는 좋은 쪽이었다. 분해능 항 `tick_ms / t` 가 32 배 작아져
> 15 us 커널에서 A6000 의 6.8 % 가 5090 에서는 0.21 % 다. 노이즈 바닥에서
> 분해능이 사실상 사라지고 `sigma_abs` 가 지배한다.

## 19. **"정의를 바꿨다" 와 "그 정의를 쓴다" 는 다르다**

P-3 은 `env_hash` 의 구 정의(= `env` 딕셔너리 전체 해싱)가 실행마다 변하는
값을 본다는 것을 밝히고 `core/env_hash.py` 에 `env_hash_v2` 를 만들었다.
문서도 충실히 썼다 — 어떤 키가 들어가고 왜 `manifest_hash` 를 뺐는지까지.

**그런데 파이프라인은 여전히 구 정의를 썼다.**

```python
env["env_hash"]    = canonical_hash(env)     # 쓰이는 것 — 구 정의
env["env_hash_v2"] = env_hash_v2(env)        # 정의된 것 — 아무도 안 읽는다
```

측정 줄(`records.py`), 재개(`sweep.resume_state`), 표와 번들(`table` /
`export` / `bundle`)이 전부 `env_hash` 를 본다. `env_hash_v2` 는
`sweep.py` 의 정합성 대조에서만 쓰인다.

5090 준비 중에 `--seed` 까지 고정하고 두 번 돌렸더니 `env_hash` 가 바뀌었는데
**해시 입력 15 개 중 달라진 것이 하나도 없어서** 드러났다. 구 해시가 본 것은
`created_utc` 와 `launch_overhead`(측정값)였다.

### 규칙

**새 정의를 도입할 때 옛 정의의 호출부를 전부 훑어라.** 옮기지 않을 것이면
왜인지 적어라 — "기존 데이터의 조회 키라 유지한다" 는 이유가 실제로 있었는데,
그 이유가 "새 정의는 아무 데서도 안 쓴다" 를 정당화하지는 않는다.

이것이 14 번(조용히 아무것도 안 함)의 변종이다. 함수는 있고, 테스트도 있고,
문서도 있는데, **호출부가 없다.** 그런 코드는 검사에 걸리지 않는다.

> 지금은 고치지 않는다. A6000 번들의 기록된 해시가 구 정의라 두 세대가 한
> 이름공간에 섞이고 `ENV_HASH_DEF_VERSION` 을 올려야 한다. **캠페인 사이에**
> `axis_space_hash` / `shape_grid_hash` 추가와 함께 한 번에 한다
> (`pending_fixes.md` D-3, D-4).
>
> 대신 **덮어쓰기를 코드로 막았다** — `phase0_env.py` 가 기존 `env.json` 과
> `env_hash` 가 달라지면 거부하고 `--force` 를 요구한다. 규칙을 사람이
> 기억하는 대신 코드가 막는다.

## 20. 시간 예산 프로토콜에서 **빠른 GPU 는 캠페인을 단축하지 않는다**

`target_ms = 20` 은 시간 예산이다 (10 번). 빠른 GPU 는 같은 20 ms 안에 반복을
더 돌 뿐이고, 작업당 GPU 시간의 상한은 GPU 와 무관하게
`probe 5 + warmup 20 + measure 20 = 45 ms` 다.

**그래서 일정은 GPU 성능이 아니라 작업 수로 잡는다.** 5090 은 A6000 보다
빠른데 작업 수가 1.287 배(`split_k` 축 8 -> 10)라 캠페인이 오히려 길어질 수
있다 (최악 19.7 h vs A6000 15.3 h).

### 그런데 그것이 낭비가 아니다 — **정밀도를 산다**

같은 20 ms 안의 추가 반복은 그대로 노이즈 바닥을 낮춘다. 그리고 5090 은
계측 분해능이 이미 훨씬 좋다:

```
이벤트 눈금   A6000 1.024 us  ->  5090 32 ns      (1/32)
15 us 커널의 분해능 항   6.8 %  ->  0.21 %
```

분해능이 사실상 사라지므로 노이즈 바닥에는 통계 항만 남고, 그 항은 반복
수로 줄어든다. **"시간이 안 줄어드는 대신 정밀도를 산다"** 가 정확한 서술이다.

일정을 보고할 때 이 교환을 함께 적어라 — 안 적으면 "느린 캠페인" 으로만
읽힌다. 정산은 G-7 의 노이즈 계수다. A6000 계수
(`sigma_abs 0.000374 ms`, `sigma_rel 0.00044`)와 나란히 놓고 비교하라.

## 21. 클럭 검증은 **실제 캠페인 경로로** 해야 한다

5090 에서 클럭 고정을 세 가지 부하로 검증했다. 셋 다 통과했다.

```
verify_clock_lock 과 같은 부하 (단일 커널, 8192x4096x4096)   294 W   20분  유지 100%
혼합 soak (config 8 x 형상 8)                                336 W   22분  유지 100%
cuBLAS 대형 지속                                             389 W    5분  유지 100%
```

**그리고 G-6 에서 `rehearse` 를 2.3 분 돌리자 바로 깨졌다:**

```
실제 캠페인 부하   중앙 434 W / ★ 최대 542 W
클럭이 2580 까지 내려갔다 (목표 2692 대비 -4.2 %)
```

**설계한 부하 셋이 전부 실제보다 가벼웠다.** 15 번의 또 다른 사례다 —
재려던 것("캠페인 부하에서 클럭이 유지되나")과 잰 것("이 합성 부하에서
유지되나")이 달랐다.

### 규칙

**합성 부하로 클럭을 검증하지 마라.** 전력 프로파일이 달라 스로틀 트리거를
재현하지 못한다. `rehearse` 를 2~3 분 돌리는 것이 20 분 soak 보다 대표성이
높다. 실제 캠페인은 커널 종류·형상·`split_k`·cuBLAS 참조가 빠르게 교대하며,
그 교대 자체가 전력 스파이크를 만든다.

그리고 **딥이 398 W 에서도 났다.** 트리거는 평균 전력이 아니라 1 초
샘플링으로는 안 보이는 순간 스파이크다. 평균 전력에 여유가 있다고
안심하지 마라.

## 22. ⛔ `sw_power_cap` 은 GeForce 에서 **클럭 감소의 신호가 아니다**

`verify_clock_lock.py` 의 판정은 A6000 에서 만들어졌다:

```python
if swpc > 0.10:  verdict = "lower"      # sw_power_cap 이 10% 넘으면 클럭을 낮춰라
```

A6000 에서는 맞는 신호였다 (미고정 51 % / 고정 0 %). **5090 에서는 아니다.**

2392 MHz 로 고정하고 `rehearse` 를 돌린 결과:

```
sw_power_cap        51/160 = 31.9 %          <- 기준의 3 배
★ 그 51 개 샘플의 클럭   전부 2392 (= 목표값 그대로)
★ 그 51 개 샘플의 전력   171 ~ 461 W          <- 171 W 에서도 뜬다
```

**플래그가 뜬 동안 클럭은 한 번도 안 내려갔다.** GeForce 에서 이 비트는
"부스트가 더 못 올라가는 이유가 전력이다" 를 뜻하고, **클럭을 부스트 상한
아래로 고정해 두면 그 말은 자명하게 참**이다.

### 규칙 — 판정은 **클럭 분포**로 하라

```
2692 고정   {2692:139, 2685:19, 2677:2, 2625:1, 2580:1}   최대 이탈 -4.2 %
2392 고정   {2392:141, 2385:19}                            최대 이탈 -0.29 %
```

목표보다 낮은 샘플의 **비율**(14.2 % -> 11.9 %)보다 **이탈 폭**이 중요하다.
2392 에서 남은 2385 는 지원 클럭 목록의 바로 아래 칸(7 MHz)이고, 그 구간의
전력이 오히려 더 낮다(중앙 323 W vs 342 W). **전력 때문이 아니라 부스트
알고리즘의 입도**이므로 더 낮춰도 안 없어진다.

`pending_fixes` 에: `verify_clock_lock` 의 판정을 스로틀 플래그가 아니라
클럭 분포(목표 미만 비율 + 최대 이탈 폭)로 바꿔야 한다.

## 23. **docstring 이 옳고 코드가 틀린 경우가 가장 찾기 어렵다**

`drift_check()` 은 docstring 에 "돌려주는 값은 **작은 형상** 쪽이다 — 감시의
민감도가 거기서 나온다" 라고 적혀 있었고, 상수 목록(`DRIFT_SHAPES`)도 맞았고,
그 코드를 넣은 커밋 제목도 "…**작은 형상 감시**" 였다. **한 줄만 틀렸다** —
`p = DRIFT_SHAPE` 가 `DRIFT_SHAPES[-1]`, 즉 가장 **긴** 형상이었다.

그 반환값이 `t_drift` 가 되어 중단 판정과 `drift_ratio` 기록을 전부 이끈다.
**24 시간 캠페인의 1 차 안전망이 A6000 이 실패한 그 방식으로 돌고 있었다.**

읽는 사람은 docstring 을 믿고 코드를 안 본다. 주변이 전부 맞으면 더 그렇다.

### 규칙

**"이 함수가 돌려주는 값이 무엇을 이끄는가" 를 따라가라.** 반환값이 판정·중단·
기록을 이끄는 함수는 docstring 이 아니라 `return` 문을 봐라. 그리고 그
불변식을 테스트로 고정하라 — `tests/test_contracts.py` 가 이제
`return m_mon.time_ms` 를 소스에서 확인한다.

> 발견 경위도 기록해 둔다. 전수 시작 전 감시 계획을 세우며 "드리프트 프로브에
> 짧은 형상이 있는가" 를 확인하다 나왔다. **체크리스트 항목이 실제로 값을
> 했다.**

## 24. 산문을 grep 해서 판정을 재구성하지 마라

`gate_g7.py` 가 `core/anchors.py` 의 판정 결과를 이렇게 읽었다:

```python
seg_fail = [f for f in rep.failures if "세그먼트 간 편차" in f]
abs_fail = [f for f in rep.failures if "절대값" in f or "단조" in f]
```

`rep.failures` 는 **사람이 읽는 설명 문자열**이다. 그리고 절대값 실패 메시지가
이랬다:

> 짧은 앵커의 절대값이 라운드 0->3 사이에 7.03 % 움직였다 (노이즈 바닥
> 6.63 %). **세그먼트 간 편차가 작아도** 전체가 함께 드리프트한다는 뜻이다.

**"세그먼트 간 편차는 문제없다" 고 설명하는 구절이 "세그먼트 간 편차 실패" 로
분류됐다.** 실패 1 건이 2 건으로 세어졌고, G-7 이 5 개 중 3 개 실패로 나왔는데
`check_anchors` 는 같은 데이터에서 1 건만 보고했다.

### 규칙

**판정은 구조화된 값으로, 산문은 사람에게만.** `AnchorReport.failure_kinds`
(`(종류, 설명)` 쌍)를 만들고 `rep.failed(FAIL_*)` 로 조회한다. 설명 문구를
고쳐도 판정이 안 바뀐다.

`tests/test_anchors.py` 가 `gate_g7.py` 소스에 `rep.failures if` 패턴이 없는지
검사한다.

## 25. **"그럴듯한 범위" 를 첫 환경의 값 배수로 정의하지 마라**

5090 을 붙이면서 A6000 전제가 코드에 박혀 있는 곳을 **네 군데** 찾았다.

| 곳 | A6000 전제 | 5090 에서 |
|---|---|---|
| `verify_clock_lock` 판정 | `sw_power_cap > 10%` (미고정 51% / 고정 0%) | 클럭이 완벽해도 31.9% 뜬다 |
| `verify_clock_lock` 판정 | `max(pw) <= 250` (300 W 캡) | 600 W 캡의 41% 라 "올려라" 가 나온다 |
| `check_anchors` 3 번 서술 | "노이즈 바닥의 정의 그 자체" (눈금 1.024 us) | 눈금 32 ns — 64 눈금 이동은 실제 신호 |
| **`TICK_PLAUSIBLE`** | `(0.2, 5.0)` × A6000 눈금 → 205~5120 ns | 실측 **32 ns 가 범위 밖** |

### 넷째가 가장 나쁘다 — 범위 밖에서 **거부가 아니라 대체**를 한다

```python
if est and lo * base.tick_ms <= est <= hi * base.tick_ms:
    return NoiseCoef(..., est, ...)          # 관측값을 쓴다
return NoiseCoef(..., base.tick_ms, ...)     # ★ A6000 값으로 대체
```

앞의 셋은 **틀린 판정**을 내지만 사람이 출력을 보면 이상하다는 것을 안다.
넷째는 **조용히 틀린 값을 넣는다.** 32 배 더 좋은 타이머를 관측하고도 버리고
A6000 눈금을 쓴다 — 그러면 83 us 형상의 노이즈 바닥이 0.084 % 대신 1.234 %
가 되고, `answer_set()` 의 정답 집합이 15 배 넓어진다.

**14 번(조용히 아무것도 안 함)의 변종이다** — 여기서는 아무것도 안 하는 것이
아니라 **조용히 다른 것을 한다.** 더 나쁘다.

### 규칙

* **범위는 절대값으로 정의하라.** "A6000 눈금의 0.2~5 배" 가 아니라
  "1 ns ~ 10 us" 다. 물리적으로 가능한 범위는 환경과 무관하다.
* **범위 밖이면 대체하지 말고 실패하라.** 폴백이 필요하면 그 사실이 출력과
  기록(`source` 필드)에 남아야 하고, 캠페인 조건에 들어가야 한다.
* **새 환경을 처음 붙일 때 "이 상수가 어느 환경에서 나왔나" 를 전수 조사하라.**
  `grep -n "A6000\|1350\|7601\|1\.024\|300W"` 로 시작하면 된다.

## 26. 격자(양자)는 **절대값이 아니라 간격**으로 추정하라 — 18 번의 정정

18 번에서 "정수배로 보이는 것은 양자화의 증거가 아니다. 격자를 직접
확인하라" 고 적고, 짧은 커널 10,000 회의 **최소 간격**을 보아 눈금을
**32 ns** 로 결론냈다. 그 결론이 **틀렸다.**

전수 캠페인의 앵커 1,152 행(고유값 36 개)으로 다시 재니:

```
 8 ns -> 설명력 100 %      16 ns -> 100 %      32 ns -> 81 %      48 ns -> 42 %
```

**진짜 눈금은 16 ns 였다.** 32 ns 는 81 % 밖에 설명하지 못한다 — 처음
표본(92 고유값)에서는 16 ns 간격이 우연히 안 나타났을 뿐이다.

### 왜 처음에 못 봤나 — 그리고 검증마저 무너진 이유

새 계수를 뽑을 때 최소 간격이 `16.0038 ns` 로 나왔다. `.0038` 은
부동소수 잡음이다. 그 후보로 **절대값**의 격자 적합도를 세었더니
설명력이 **3 %** 였다 — 격자가 맞는데도.

```
0.72 ms 짜리 값은 16 ns 눈금의 45,000 배다
후보의 0.0038 ns 오차 x 45,000 = 180 ns = ★ 11 눈금
-> round(x / cand) 가 엉뚱한 정수를 고른다
```

**큰 배수에서는 후보의 미세 오차가 눈금을 넘는다.** 절대값으로 격자를
검증하는 방법 자체가 거기서 무너진다.

### 규칙

1. **간격으로 재라.** 양자는 차이에 나타난다. 간격은 작은 배수라 반올림이
   안정적이다.
2. **정수 물리량이면 정수로 스냅하라.** 하드웨어 타이머 양자는 정수 ns 다.
   `16.0038 -> 16` 으로 스냅한 뒤 검증하면 설명력이 3 % -> 100 % 가 된다.
3. **설명력이 같으면 가장 거친 후보를 골라라.** 8 ns 도 100 % 지만 그것은
   16 ns 격자 위의 값을 전부 설명하기 때문이다 (세밀한 격자는 항상 이긴다).
   과대 분해를 피하려면 통과한 것 중 최대를 쓴다.

`core/noise.py::tick_grid()` 가 이 셋을 한다. 새 환경에서는 `tick_ms_observed`
(최소 간격)를 **판정에 쓰지 마라** — 진단용이다.

> 18 번의 교훈("격자를 직접 확인하라")은 그대로 옳다. **그 확인을 어떻게
> 하느냐가 빠져 있었다.** 확인 방법에도 함정이 있다.
