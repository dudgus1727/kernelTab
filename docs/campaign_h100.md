## 2. ★ §4 첫 관문 — `sm_90` 에서 CUTLASS 2.x 가 성립하는가

**결론: 성립한다. 다섯 항목 전부 통과.** `backends/__init__.py` 의
`get_backend` 와 `CutlassV2Backend.arch_family` 에 `sm_90` 을 넣었다.
**커널 생성부(`emit_cpp` / `TB_TILES` / `STAGES` / `is_valid_*`)는 무수정이다.**

| # | 항목 | 결과 |
|---|---|---|
| 1 | nvcc 가 sm_90 을 아는가 | ✅ `--list-gpu-arch` 에 `compute_90` |
| 2 | 2.x 가 sm_90 에서 빌드되는가 | ✅ 프로브 25/25 + **무작위 표본 240/240** (100 %). `cuobjdump -lelf` 로 `*.sm_90a.cubin` 확인 |
| 3 | **참조값 대조** | ✅ 실행된 24 개 전부 `max_rel_error = 0.000e+00` (cuBLAS `COMPUTE_32F` 대조). 나머지 1 개는 `launch_infeasible`(regs 137 × threads 512 = 70,144 > 65,536) — 저장소의 `kernels.launchable()` 이 이미 거르는 경로다 |
| 3b | split-K serial/parallel | ✅ 두 커널 × 축 10 종 × 2 모드에서 **요청 == 실제 `grid.z` 32/32 일치**, 참조 불일치 0. serial 의 `1e-3` 대 오차는 fp16 부분합(결정 6) |
| 4 | `pipeline_kind` 의미 유지 | ✅ `stages=2` → LDGSTS **0** (4/4), `stages≥3` → 전부 > 0 (18~200). A6000/4090/5090 과 같은 갈림 |
| 5 | 축 중 몇 개가 유효한가 | 아래 3 절 |

검증 범위: alignment `a888 / a448 / a228 / a118 / a884 / a882` 전부,
stages 2~8 전부, swizzle `identity{1,8}` + 직접 구현한 `horizontal`,
tile_k 32/64 와 warp_k 분할, 그리고 **H100 에서만 유효해진 큰 smem 커널**
(smem 102 KB ~ 224 KB) 5 개.

### `env_hash` 는 어떻게 바뀌는가 (§4 마지막 확인)

* `axis_space_hash` = `401555c4…` — **바뀌지 않는다.** 예상대로다. 축 목록은
  모듈 상수(`TB_TILES`/`STAGES`/`SPLIT_K`…)에서 나오고 arch 와 무관하다.
* `shape_grid_hash` 는 바뀐다 (`sm_count` 132 → 층 C 가 달라져 **형상 68 개**).
  A6000 65 / 4090 68 / 5090 66 / **H100 68**.
* 실제 탐색 공간이 2 배가 된 것(아래)은 `hardware.smem_per_block` 가
  `env_hash` 의 `hardware` 에 들어 있어 **간접적으로** 덮인다.
  ⚠️ 축 목록이 같아도 **유효 공간이 GPU 마다 다르다**는 것이 이번에 처음
  드러났다. `axis_space_hash` 만 보고 "같은 공간" 이라고 하면 틀린다.

## 3. ★ 탐색 공간이 5090 의 2 배다 — smem 227 KB 때문

| | A6000 / 5090 | **H100 NVL** |
|---|---:|---:|
| smem(optin) | 101,376 B | **232,448 B** |
| 열거 커널 | 7,230 | **13,975** |
| 그중 H100 에서만 유효 | — | **6,745** |
| 런치 가능 (표본 240 추정 82.9 %) | 5090 6,305 | **약 11,580** |
| 형상 | 66 | **68** |
| (형상 × 커널 × 런타임) 작업 | 1,262,825 | **2,906,225** (열거 기준) |

같은 코드에 smem 만 101,376 을 넣으면 정확히 **7,230** 이 나온다 — 즉 차이의
원인은 전부 `smem_capacity` 제약이다. 새로 열린 6,745 개는 `stages` 5~8 과
`tile_k=64` 쪽에 몰려 있다.

**일정 영향**: 5090 의 작업당 67.9 ms 를 그대로 쓰면 2.9 M × 67.9 ms ≈ **55 시간**
(런치 가능 필터를 적용하면 약 45 시간). H100 이 빠르지만 시간 예산
프로토콜에서는 GPU 속도가 캠페인 길이를 거의 바꾸지 않는다(결정 20).
**세그먼트 수가 늘어 재시작 횟수도 늘어난다 — G-4/G-5 에서 다시 계산할 것.**

## 4. ★ FP32 누산 반감 실측 — **없다**. 그런데 다른 문제가 나왔다

`tools/peak_mma_probe.cu` 를 **새로 작성했다** (§6-4 는 4090 캠페인에서
만들었다고 하지만 저장소에 없다). 메모리 접근 없는 `mma.sync.aligned.m16n8k16`
루프 + `clock64()`.

```
FP32 누산   1324.0 FMA/clk/SM   554.7 TFLOP/s @ 관측 1587 MHz
FP16 누산   1365.1 FMA/clk/SM   569.1 TFLOP/s @ 관측 1587 MHz
비율 1.031  ->  ★ 반감 없음 (A6000 계열, GeForce Ada/Blackwell 과 다르다)
역산 클럭 1587 / 1587 MHz 일치  ->  측정 건전
warp 4~24 x 독립누산기 4~16 스윕에서 1323.4~1324.0 로 포화 (포화 확인)
```

### ⚠️ 새로 드러난 것 — mma.sync 로는 데이터시트 피크에 못 간다

| 경로 | 실측 | 1785 MHz 환산 |
|---|---:|---:|
| **mma.sync** (= 우리가 재는 CUTLASS 2.x) | 554.7 TFLOP/s @1587 | **623.9** |
| cuBLAS `COMPUTE_32F` 4096³ (wgmma 경로) | 717.4 TFLOP/s @~1590 | ~806 |
| 데이터시트 (dense, FP32 누산) | — | ~835 |

Hopper 의 최고 처리량은 **wgmma(warpgroup async, 3.x API)** 에서만 나온다.
`mma.sync` 는 서브파티션당 HMMA.16816 을 6 사이클에 하나씩 내는 것이 상한이고
(4 × 2048 / 6 = 1365.3 — 실측 1365.1 과 일치), 그것이 위 표의 1.29 배 격차다.

**A6000/4090/5090 에서는 이 구분이 없었다** (mma.sync 가 곧 하드웨어 피크였다).
H100 에서 처음으로 **"이 표의 config 공간이 GPU 의 피크에 도달할 수 없다"**
가 됐다. `peak_tflops_f16` 은 ridge point 의 분자이자 `frac_of_peak` 의
분모이므로 선택이 결과의 의미를 바꾼다.

```
mma.sync 623.9 를 쓰면    ridge = 623.9 / 4022.8 = 155.1 FLOP/byte
데이터시트 835 를 쓰면    ridge = 207.6            (A6000 159.1 / 5090 117.9)
```

**현재 `known.json` 에는 mma.sync 값(623.9)을 넣었다.** 근거: `frac_of_peak`
와 `is_memory_bound` 는 **실제로 도달 가능한 값** 기준이어야 하고, 이
하네스는 2.x 만 잰다. 도달 불가능한 피크를 쓰면 전 형상의 `frac_of_peak` 가
구조적으로 25 % 깎이고 bound 분류가 통째로 이동한다.
**되돌리려면 `hwspec/known.json` 한 줄이다 — phase0 전에 결정할 것.**

## 7. G-0b 축 덮개 — **exit 0**, 3.x 추천 없음 (2026-09-02)

```
추천 612 건 / 68 형상 (nvidia-matmul-heuristics, target=CUTLASS, 프리셋 H100_NVL)
cluster : 612/612 이 (1,1)          instr : 612/612 이 (16,8,16)   ★ 3.x 아님
공간 밖 : 17/612 = 2.8 %  전부 stages=1 (근거 있음 — 수치가 틀리는 값이다)
```

A6000 6.0 % / 5090 17.8 %→2.8 % / 4090 2.8 % / **H100 2.8 %**. 축 구멍 없음.

> ⚠️ `GPU_PRESETS` 에 `h100 nvl` 을 넣기 전에는 `h100` 이 먼저 걸려 **H100_SXM
> 프리셋**이 조용히 쓰였다. 변종마다 SM 수·메모리가 다르므로 그대로 뒀으면
> 다른 GPU 의 추천으로 축 덮개를 판정할 뻔했다.

### ★ 벤더 추천의 62.6 % 가 A6000/5090 공간 밖이다

같은 추출물에서 각 추천의 smem 을 계산해 봤다.

| | 건수 | 비율 |
|---|---:|---:|
| smem > 101,376 B (A6000/5090 이 못 담는 config) | **383 / 612** | **62.6 %** |
| ★ 형상별 **top-1** 추천이 그런 config 인 경우 | **29 / 68** | **42.6 %** |

즉 `stages` 7~8 과 큰 타일이 H100 에서 벤더의 주력 추천이다. 이 영역을 안
재면 **벤더 baseline 을 채점할 수 없다** — 벤더가 1 순위로 고른 config 가
표에 없는 형상이 68 개 중 29 개가 된다. `split_k` 5·7 구멍과 같은 논리다.

## 8. G-3 잠정 (클럭 미고정 상태의 값 — 고정 후 다시 잰다)

### 눈금 = **32 ns**

`tools/tick_probe.cu` + `tools/tick_report.py` 를 새로 썼다. 목표 길이
2 us ~ 2 ms 여섯 구간 × 800 회.

```
전 구간에서 32 ns, 설명력 100 %
16 ns 후보는 설명력 100 % 이지만 ★ 홀수 배수가 0.0 % -> 기각
                                  (32 의 절반이라 짝수 배수만 관측된다)
64 ns 이상은 설명력 50 % 이하
A6000 1024 / 4090 32 / 5090 16 / ★ H100 32 ns
```

### SOL 하한 — ⛔ 여섯 형상이 문턱 아래, 그중 넷이 층 A 다

`below_launch_overhead` 문턱 = 3 × 3.584 us = **10.752 us**
(5090 은 12.288 us. H100 의 런치 오버헤드가 더 작다).

| 형상 | SOL @1785 | 문턱 대비 | @1400 가정 | 지배 | 층 |
|---|---:|---:|---:|---|---|
| `1x4096x4096` | 8.35 us | **77.6 %** | 77.6 % | memory | A |
| `8x4096x4096` | 8.37 | **77.9 %** | 77.9 % | memory | A |
| `32x4096x4096` | 8.47 | **78.8 %** | 78.8 % | memory | A |
| `128x4096x4096` | 8.86 | **82.4 %** | 82.4 % | memory | A·C |
| `2048x4096x256` | 6.88 | **64.0 %** | 81.6 % | compute | B |
| `4096x4096x128` | 8.86 | **82.4 %** | 82.4 % | memory | B |
| `256x4096x4096` | 13.77 | 128.1 % | 163.2 % | compute | A·C |
| `4096x4096x256` | 13.77 | 128.1 % | 163.2 % | compute | B |

**★ 메모리 바운드인 것은 SM 클럭을 고정해도 안 움직인다** — 메모리 클럭이
2619 하나뿐이기 때문이다. 즉 넷은 **어떤 클럭 조건에서도 문턱 아래**다.

이 구간이 가장 나쁜 자리다 (문턱의 64~82 %): 느린 config 는 살고 **빠른
config 만 잘린다.** 결측이면 차라리 낫다.

원인은 H100 의 대역폭이다. `M<=128 x 4096 x 4096` 은 B(33.5 MB)를 읽는
시간이 지배하는데 4.0 TB/s 면 8.4 us 다 — 런치 세 번보다 짧다. 같은 형상이
5090 에서는 19 us(문턱의 155 %)였다.

앵커(`DRIFT_SHAPES` 2048³/4096³)는 문턱의 256 % / 2049 % 로 **안전하다.**

> 층 A 의 다른 세 (N,K) 열은 M=1 에서도 209~233 % 로 살아남는다. 문제는
> **`(N,K) = (4096,4096)` 열 하나**다.

## 9. 컨테이너 — rootless docker 가 된다

```
docker 29.7.2 rootless  (uidmap/subuid/linger/user-systemd 전제조건 전부 충족)
nvidia-container-toolkit 설치돼 있고 no-cgroups = true 도 이미 켜져 있다
apparmor_restrict_unprivileged_userns = 0 (Ubuntu 24.04 인데 제한이 꺼져 있다)
```

**★ forward-compat 이 얹힌다** — 호스트 커널모드 570.158.01(CUDA 12.8) 위에서

```
로드된 libcuda : /usr/local/cuda-13.3/compat/libcuda.so.1 -> 610.43.02
cuDriverGetVersion : 13030   nvcc : 13.3.73   device : H100 NVL sm_90
```

**5090·4090 과 같은 610.43.02 다.** 즉 컨테이너로 가면 CUDA·CUTLASS·유저모드
드라이버가 앞 캠페인과 완전히 같아지고, **바뀌는 변수는 GPU 와 커널모드
드라이버 둘뿐**이 된다.

## 11. 커널 빌드 — `static_assert: Too many predicates.`

그리고 그 앞에도 두 번 더 있었다 — 버퍼 크기 모델(큰 버퍼가 느릴 것),
